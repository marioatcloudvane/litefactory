# Brainstorming a feature

When the owner wants to brainstorm a feature, work it out in conversation first. Keep answers short and plain, so they are easy to hear when spoken.

1. Ask what the goal is and who it helps.
2. Ask what is in scope and what is not. Write down the non-goals.
3. Collect the open questions. Ask them one at a time.
4. Say back a short summary and ask what is missing.

If the owner shares a document, read it in this chat and pull out only what matters. Name the document as the source. The factory does not take, keep or forward the document itself.

A brainstorm only reads. Use only the read tools you already have. It writes no code, edits no issues, and only warns about possible duplicates. It never closes or merges them.

Nothing is created or approved from a brainstorm alone. Creating issues or starting Plan needs the normal proposal and a separate yes from the owner. That yes approves only creating issues and starting Plan. It approves no Plan stage.

Brainstorm tools exist only when your tool list has them, under the owner's repository brainstorm consent. Without them, keep the brainstorm in this chat, say there are no brainstorm tools for this connection, and do not try to call one.

When you have them, keep the brainstorm in the factory so nothing is lost between chats:

1. Open or resume the brainstorm for the repository first.
2. On resume, read every kept entry and every earlier question, page by page to the end, so no earlier question or answer is forgotten. Do not ask again what is still waiting or running.
3. Send every factual question about the repository to the factory's research question tool, one question per call. Do this yourself, without asking the owner first and without the owner having to mention a scan. Each question starts one paid read-only run.
4. When the owner asks whether there is already an issue for something, search the issues. A match is a warning to check, never proof of a duplicate.
5. When an answer arrives, read its spoken answer aloud as it is.
6. Keep ideas, decisions, open questions and related issues as entries. A note from a shared document always carries the document's name.

When the owner is done and your tools can make drafts, turn the brainstorm into tasks:

1. Ask the factory for drafts. It turns the kept brainstorm into one to five task drafts. This is one more paid read-only run.
2. Read the spoken summary and each draft aloud: title, size, impact and any possible duplicate. A possible duplicate is a warning, never proof.
3. Ask the drafter's open questions one at a time. Keep each answer in the brainstorm as a decision, so the next drafts use it.
4. Let the owner drop any draft. Only the drafts the owner keeps go on.
5. If your tools can create tasks, propose creating the kept drafts. Read the proposal back. Confirm only after the owner says yes in a separate message.
6. Then read the outcome of every draft and say it plainly, with its issue number when known.

A draft counts as started only after its brief is ready and Plan's first agent runs. If the factory cannot tell yet whether an issue was made, say so plainly: the issue is not identified yet, nothing was duplicated, not found in search is not proof it was not created, and the factory keeps checking for a while. Never ask to create it again on your own. When the checks run out, only the owner can ask for a new issue, and that may lead to two issues for the same draft.

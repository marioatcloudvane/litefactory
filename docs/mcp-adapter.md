# MCP adapter foundation

`litefactory mcp serve --descriptor /absolute/private/descriptor.json` serves the current live launch over stdin/stdout. It checks the existing private broker before starting. Factory credentials remain outside this process. Only protocol JSON is written to stdout; errors returned to the CLI are fixed, bounded diagnostics.

This endpoint implements the [MCP 2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), [stdio transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) and [tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) subset. Initialize negotiates the sole supported version, 2025-11-25, even when the client requests another version. A client unable to use that response must disconnect. An initialized notification is required before tools/list or tools/call. Only the tools capability is advertised. HTTP, prompts, resources, sampling, elicitation and Tasks are unavailable. Unknown requests and malformed state/parameters receive JSON-RPC errors; unknown notifications are ignored. IDs are strings or integer literals, at most 256 encoded bytes; fractional/exponent ID notation is unsupported.

Each MCP message is one UTF-8 JSON line. Duplicate object keys, invalid UTF-8, invalid field types and nesting beyond 32 containers are refused before forwarding. The input bound is 4 MiB plus 64 KiB of envelope space, preserving the existing 4 MiB contribution ceiling. The private socket retains its length-prefixed protocol with a 16 MiB frame limit to accommodate result snapshots plus base64 receipt payloads. MCP output is capped at 64 MiB because it includes both the structured response and compatible escaped JSON text; input size and conservative preallocation bounds constrain both encodings. HTML escaping is disabled in this protocol serialization to avoid unnecessary sixfold expansion. Oversize input terminates the connection with a bounded failure; oversize backend output receives an internal error rather than an unbounded response.

A connection owns one reader, one serialized writer and at most four tool workers. At most eight responses are queued; backlog overflow terminates the connection. Active IDs remain reserved until output completes. Cancellation targets only a matching active connection-local request; initialization cannot be cancelled. Unknown/completed cancellation IDs are ignored. EOF or cancellation closes the owned input/output streams and joins all workers. The Server.Run stream contract requires Close to interrupt Read/Write (real process pipes and io.Pipe satisfy it); arbitrary noninterruptible wrappers are unsupported. A backend must honor context cancellation. No worker is detached to simulate cancellation.

The three tools are communication_preflight, communication_submit and communication_receipt. Their argument object is the existing exact JSON result contribution or, for receipt, `{ "request_id": "retained-application-id" }`. Submission journals choose durable request IDs independently of MCP IDs. Results preserve validation diagnostics and separate input, engineering, acceptance and publication states; pending never means workflow success. Domain refusal is an MCP tool error result, with JSON text and structuredContent containing the existing submission response. Transport/structural failure uses JSON-RPC errors. Disconnect never implies rollback or remote success: reconnect with the same live descriptor, handshake again, and inspect the retained application correlation.

Tool visibility belongs only to this server. Existing permitted native tools and unrelated MCP servers retain their host policies. Research and Spike communicate their own results; Implement remains frozen-scope bound; Validate communicates retained assessments without execution capture or self-acceptance. No shell, execution, waiver, dispatch, mode change or creation tool is advertised. Plan discussion without publishable stories is supported. MCP submits that would retain completed/story-bearing Plan proposals are explicitly refused after shared validation, including updates to existing proposals and recovery. Ordinary helper Plan publication policy remains unchanged.

## Automatic registration consumer contract

`settings.mcp_auto_start` defaults to true; explicit false omits automatic registration. It is a strict boolean loaded at startup, without hot reload. This convenience setting does not enable creation, mint a grant or widen mode/sandbox permissions. Explicit serving still works with false when the descriptor has live authority. An idle daemon starts no MCP child and receives no authority from this setting.

After binding the existing real cold/resume/fallback launch, the factory supplies that attempt reference to submission.Options.AttemptReference. BuildMCPLaunchSpec checks the live guard, live private broker files and matching reference, then returns an optional immutable agent.MCPLaunchSpec: absolute resolved executable, fixed structured arguments `mcp serve --descriptor <absolute-path>`, private descriptor path and existing attempt reference. Arguments returns a fresh slice. The optional agent.Request.MCPLaunch field is distinct from Permissions. Construction starts no process and writes no host configuration. Missing active attempt or disabled policy produces no registration; stale/mismatched construction fails.

#272 prepares this registration foundation. #264 owns production launch adoption and lifecycle wiring; #274 owns provider-specific consumption, server merging, actual child startup/teardown and authentic connection/isolation evidence. Host consumption is currently unavailable: prepared data and a true setting are not a connected host. #273 owns future real tool families and publication logic; it must consume the separate creation grant primitive instead of treating communication or visibility as creation permission.

## Exact owner creation approval

`settings.allow_mcp_story_creation` defaults to false in settings and the template. It is a strict boolean loaded at startup, without hot reload. The initial catalog still advertises no creation tool even when enabled. A future real creation handler must use CreationAuthorizer.CreationVisible for discovery and ReserveCreation/BeginDispatch for execution; the gate alone grants no creation authority. Research is the sole eligible mode, and Validate is always refused.

The factory first retains a version-1 canonical CreationEnvelope with repository, source task, linked/attach relationship and every exact artifact title, body, parent and link target. The future #273 family owns rendering/normalization before this step. The public hash fingerprints that exact typed content; it is not a password. Only the owner-controlled intake accepts a whole exact command:

```
/mcp-create <proposal-sha256> linked
/mcp-create <proposal-sha256> attach
```

The authorizer fixes the configured numeric owner/bot IDs when constructed. The daemon passes retrieved GitHub author/comment IDs, creation/update timestamps and the source repository/issue separately from the body. Wrong owner, bots, quotes, copied commands, malformed syntax, wrong mode/source/relationship, absent or changed proposals and stale approval are refused. The proposal must already have existed when the approval comment was created. The first retained intent for a comment is immutable; changing content needs another explicit approval. Changing the current proposal and then restoring an older hash does not revive the older intent.

Approval expires exactly 30 minutes after the trusted comment creation timestamp. Intake delay, edits, launch allocation and reconnect never extend it. Consumption binds the intent to one next eligible actual factory launch; the existing MCP lease records its binding time and must follow approval. Grant expiry is the earlier of the original deadline and attempt expiry. Reuse on resume/fallback/replacement is refused. No elevated bearer credential is placed in public comments, descriptors, MCP arguments/results or prompts; grants remain factory database records.

CreationStore uses one short transaction to recheck the live lease, broker instance, exact approved envelope/current proposal, grant and quota. Conservative fixed caps are one batch and five artifacts per attempt, and twenty artifacts per repository per rolling 24 hours. Each issue/subissue consumes one unit. Confirmed batches count within that window; pending, uncertain and unreleased failures remain charged regardless of age. Repository budgets are isolated. Overflow is an immediate refusal, not a queued retry.

A successful reservation owns one durable operation. Only its first admission receives an internal, nonserializable dispatch permit. Concurrent/retried requests return the same operation with no second permit. BeginDispatch rechecks lease/grant/content expiry and consumes dispatch once before external I/O. No transaction spans that I/O. Cancellation/restart never restores the grant or elects another dispatcher. Already owned effects can still record their truthful outcomes after revocation, while separate factory-only reconciliation can inspect and update recorded operations without renewed agent authority.

Operation states are reserved, dispatched, confirmed, uncertain, failed and released. Only a definitively never-dispatched reserved/failed operation can release quota; that never reopens its consumed grant. Partial or unknown remote results remain uncertain and fully charged. Confirmed/released states cannot be reversed through this primitive. The local permit/reservation guarantee is not remote GitHub exactly-once delivery.

CreationStore and CreationAuthorizer control methods, raw operation recovery and daemon.AdmitMCPOwnerCommand are trusted factory APIs, not model-callable endpoints. The groundwork deliberately performs no actual issue publication or live comment polling. #264 later connects trusted control intake and fresh launches; #273 implements real family effects/reconciliation; #274 verifies authentic host isolation. Loading either setting does not establish those connections.

## Cancellation and recovery handoff

MCP connection state and application state have separate owners. `Server.Run` cancels its client requests and joins its stream/call workers. The submission client closes its private socket when its request context ends; the broker's bounded connection monitor cancels the corresponding handler and is joined before that worker exits. `Broker.Close` cancels and joins every remaining handler. A future family handler must propagate this context through admission and external work; returning from a transport does not establish the outcome of that work.

| Interruption point | Retained application state | Permitted next action |
|---|---|---|
| Before transaction admission | No accepted result or creation reservation | A still-live authorized caller may retry the exact contribution using the existing journal correlation. |
| After result admission, before response delivery | Original durable request and receipt dimensions | Reconnect and query the receipt or replay the exact request under live scope. |
| After creation reservation, before dispatch | One reserved operation and one dispatch owner; quota charged | That original owner may call `BeginDispatch` while lease and grant remain valid, or record a proven never-dispatched outcome. A duplicate receives no permit. |
| After dispatch admission, before remote acknowledgement | Dispatched operation; effect may be unknown | The owner records the observed outcome; unknown/partial effects remain uncertain and charged. Reconciliation must observe the existing operation. |
| Attempt cancelled, replaced, expired or closed | Recorded work remains; old authority is refused | Factory-owned recovery can inspect history. A separately live, scoped result reader can inspect permitted receipts; it receives no creation dispatch authority. |
| Broker or daemon restart | Journals, operation identity, outcomes and quota remain | The new runtime invalidates all old leases/grants. Reconciliation cannot mint a replacement dispatch permit or automatically repeat uncertain creation. |

The first creation reservation's permit belongs to the factory handler. It must never be returned through MCP. After cancellation, the factory may record a known outcome using its own bounded recovery context and the retained operation/ownership, independently of the cancelled agent context. `RecordOperationOutcome` and `ReconcileOperation` record facts and never dispatch. The consumer must not turn a timeout into `never_dispatched` after dispatch was admitted. This primitive intentionally keeps dispatched failures charged until a justified outcome is recorded; it does not infer rollback from a closed channel.

Same-live-attempt reconnect uses the same descriptor and submission journal, performs a new MCP handshake and passes broker/guard authorization again. It allocates no capability or grant. The client journals exact contribution bytes before sending a mutation, so a lost response can be retried without choosing a second application identity. Expired grants refuse exact creation replays as well as new creation calls. Result receipt reads have separate live scope checks; factory-internal historical access remains available without restoring agent authority.

The initial communication surface cannot retain a completed or story-bearing MCP Plan proposal: shared validation records a refusal and leaves the accepted result revision unchanged. Recovery therefore has no newly accepted MCP publication candidate to consume. Replaying a previously accepted helper proposal through MCP is also refused, while authorized receipt inspection and the original helper policy remain intact. A future family that admits deferred creation must carry its factory-authenticated effect restriction through its own durable publication and recovery path; merely hiding a tool or remembering its origin in connection memory is insufficient.

Offline pipe/socket/SQLite fixtures establish local cancellation, admission, identity and recovery behavior. They do not prove remote GitHub exactly-once delivery or authentic host startup. The later consumers retain these obligations: #264 binds each real launch and trusted control intake, #273 records/reconciles actual family effects, and #274 consumes the neutral registration and verifies host startup, teardown, additive inventory and isolation. None of those connections is established by enabling either setting.

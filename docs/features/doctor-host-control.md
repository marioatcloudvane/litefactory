# Doctor local host control

The factory owns the doctor control socket under `config.Paths.DoctorControlDir`. It uses the existing private authenticated submission broker with two bounded workers, a one-minute handler limit, strict payload decoding and an instance-bound descriptor. The agent never receives this descriptor. Broker close cancels and joins handlers before the daemon releases its singleton lock.

The three local calls are target drain, restart handoff and restart observation. Each request must identify the currently advertised daemon instance. Drain requires an already installed exact repair hold and joins the target writer/process lifecycle through `Daemon.DrainDoctorTarget`. Neither PID liveness nor a failed socket connection establishes exclusion. After stale control failure, the down path must acquire the actual daemon singleton lock; a live holder causes refusal.

A verified repair commits its restart token before dispatch. Host dispatch creates an immutable private marker before any process start. Existing markers, start failures and lost replies require observation rather than another start. Foreground/down recovery starts the pinned same factory executable with fixed `daemon run --doctor-repair ... --doctor-token ...` arguments, a separate session, no terminal and the factory-owned environment. Credentials resolve normally in the replacement process; the environment is never passed to a doctor agent. A changed executable is refused.

The replacement has a bounded singleton wait and rechecks the durable token after acquiring the lock. Startup recovery continues to respect durable repair holds. The local host becomes ready only after ordinary startup checks complete. It confirms recovery only for its exact supplied token and a distinct instance. The doctor service independently rereads repaired rows/files before acknowledging recovery and releasing the hold.

This host implementation does not enable either native agent isolation gate. Ordinary daemon startup continues with repair unavailable if its local control endpoint cannot be created. An explicit recovery startup refuses if its control or token cannot be established. Native isolation, authentic target process drain and real restart behavior still require the retained external observations. Tests use temporary databases, Unix sockets and fake replacement callbacks; they do not restart a live daemon.

On macOS the replacement inspects the installed default LaunchAgent. A loaded service must match the current singleton process (or be stopped on the confirmed-down path), the pinned executable, fixed daemon arguments and the exact factory home. Both the owner-private plist and loaded launchctl configuration are checked; unrecognized output fails closed. The factory retains an exact private recovery token before calling `launchd.Manager.Restart`, without rewriting the plist. Ordinary service startup reads that token before acquiring the singleton and running recovery. An acknowledged token remains history and cannot cause a second dispatch. An unloaded installation uses the pinned foreground/down entry point. Fake launchctl tests cover identity refusal and lost-reply token carryover; authentic launchd output and lifecycle observations remain unverified.

# Research brief

## Request

Shape #385 into a buildable standalone Bug workflow scope, preserving all settled owner decisions and defining records, interfaces, permissions, check recipes, recovery, validation and edge cases for owner review.

## Decisions

- **d1** — Preserve the supplied settled entry rule: bug selects a standalone workflow only without an explicit Mode label. Bug is not a sixth mode. An admitted task retains its workflow despite later relabelling.
- **d2** — Preserve two owner gates: approval of the exact analysis revision authorizes scoped repair; approval of the tested PR's exact head and target authorizes delivery. Material remedy changes return for renewed analysis approval. Only authenticated owner replies approve.
- **d3** — Preserve eight analysis passes and one shared budget of initial fix plus two repairs, consumed by test failures and PR feedback without restart or reply resets. Testing is one separately executed, durable child at a time, with recovery and cancellation; no general recursive or parallel graphs.
- **d4** — Deliver the seven Bug-only activities lf_bug_record, lf_bug_attempt, lf_bug_test_graph, lf_bug_checks, lf_bug_pr, lf_bug_merge and lf_bug_close. Checks come only from project configuration; missing recipes block. No dependency on #319, feature story lifecycle or mode handoffs.
- **d5** — Both Bug agents must have Role, Voice, Goal, How You Are Invoked, When You Are Done, Must Do, Must Not Do, Writing the Report and Output sections. Analyst investigates and shapes without product repairs; fixer makes the approved repair and regression tests. Analyst responses are ask/done/approved/blocked; fixer responses are done/reshape/blocked. Both use the shared versioned result route.
- **d6** — Preserve failure visibility and retained evidence. Skipped, interrupted, stale or flaky checks cannot pass. Changed source, recipe or target invalidates affected evidence and approval. Closure occurs only after confirmed integration; uncertain closure stays pending.
- **d7** — As an owner, I can submit a bug, approve its evidenced cause and bounded remedy, review the tested repair, and approve delivery so the factory confirms integration and issue closure without entering a feature mode.
- **d8** — The versioned bug record contains stable repository and numeric issue identity, workflow identity/version, expected and actual behavior, reproduction steps and environment, cause with evidence, remedy boundaries, exclusions, measurable success criteria with stable IDs, and immutable analysis revisions.
- **d9** — The separate versioned execution record retains parent graph identity, analysis-pass count, repair reservations, current source and target identities, recipe digest, child-call identity and state, check evidence, owner-reply bindings, PR identity, delivery intents and observed outcomes, failure reason, and pending-effect state.
- **d10** — Analysis approval binds the authenticated owner and reply to the task, review wait and exact analysis revision, while delivery approval additionally binds PR identity, tested head SHA, target repository and branch, observed target SHA and complete check evidence.
- **d11** — Use repository-root .litefactory/bug-checks.yaml schema version 1 from the recorded target commit as the project recipe source, with required regression, focused and full phases each containing a nonempty ordered commands list.
- **d12** — Each recipe command declares nonempty argv, an optional repository-relative cwd defaulting to the root, optional named environment references, and a positive timeout_seconds defaulting to 1800, with strict rejection of unknown fields, invalid versions, unresolved environment references and directories escaping the worktree.
- **d13** — Run recipes without implicit shell expansion or agent-supplied arguments in the task worktree with the normal configured permission ceiling, forward only declared environment values plus required process basics, never pass forge or result-service credentials, and stop remaining commands after the first failed command.
- **d14** — Resolve and retain the entire recipe snapshot and digest before checks, disallow repaired-branch recipe edits from changing executed commands, and require fresh checks whenever the trusted recipe snapshot changes.
- **d15** — Each check records phase and command identity, recipe digest, exact source tree and head, target repository/branch/SHA, environment-reference names, start/end observations, exit or interruption status, and redacted output evidence.
- **d16** — The child runs regression, focused and full checks sequentially and reports passed only when every command completes successfully on the same unchanged source, recipe and target binding.
- **d17** — A normal nonzero test result returns a failed child outcome and enters repair, whereas missing recipes, launch failures, timeouts, interrupted runs, known flakiness and indeterminate results stop visibly as blocked without automatic repair or pass-until-green retries.
- **d18** — One durable call identity binds parent instance, reserved repair attempt, test generation, input digest and child instance, and replay resumes that child rather than allocating another child or accepting a result with different bindings.
- **d19** — Cancellation is durably requested and propagated to the child and its running command, the parent waits for a confirmed terminal child state, and recovery preserves an unknown outcome until observation resolves it.
- **d20** — Reserve each logical fix before dispatch, count the initial fix and both repair entry paths against the same three-slot budget, and reuse a reservation only when recovering that same logical attempt rather than repeating completed fixer work.
- **d21** — Count every substantive analyst invocation against the eight-pass budget, including reshaping, but authenticate an approval reply in the factory without charging another investigation pass so the eighth completed analysis remains approvable.
- **d22** — Analyst ask publishes batched questions, done publishes the analysis for review, approved requires matching owner evidence, and blocked stops with retained cause; fixer done starts the child, reshape returns to analysis without restoring budgets, and blocked stops visibly.
- **d23** — PR feedback requesting an in-scope code change enters the same repair reservation used by test failure, material remedy changes return to analysis approval, and clarification-only feedback retains valid evidence without spending a repair slot.
- **d24** — Budget exhaustion stops with a visible report and leaves the issue open, while restart, relabelling, review replies, reshaping and infrastructure recovery never replenish counters or silently create a replacement workflow.
- **d25** — PR preparation creates or reuses one unambiguous task PR only after passing checks, verifies the remote head matches tested evidence, and presents the approved analysis, repair summary, criterion coverage and check evidence for delivery review.
- **d26** — Delivery targets main in this first version, rechecks the exact PR head, repository and target branch plus current target tip immediately before merge, and blocks for fresh evidence and approval on observed source, recipe or target drift.
- **d27** — After an uncertain PR creation, merge or close response, reconcile the recorded remote identity before retrying, refuse ambiguous PR matches, require an independent merged-PR observation before closure, and require an independent closed-issue observation before workflow completion.
- **d28** — The analyst may investigate and propose analysis records but cannot repair product files, the fixer may edit only within the approved remedy and add regression tests, and neither agent may authorize effects, select check commands, merge or close.
- **d29** — Bug agents use the nine dedicated Research/Plan markdown sections in shipped and installed copies, with role-specific duties, permissions, response vocabulary, shared-service preflight/submission/receipt handling and no terminal-text application-result fallback.
- **d30** — Bug exposes label admission, authenticated issue questions and review, the two agent roles, bug.dot and bug_tests.dot, a versioned Bug result payload, the seven named Bug activities and project recipe configuration without new mode labels or feature-story interfaces.
- **d31** — The parent graph explicitly handles every agent response, attempt result, child outcome and delivery state, and each activity error retains evidence and stops with a visible failure comment whose failed publication remains pending.
- **d32** — Approval, failure, cancellation and completion must survive duplicate owner events and daemon restarts without duplicated repairs or remote effects, and malformed results, unsupported versions, stale revisions, wrong-owner replies and mismatched evidence must fail closed.
- **d33** — Scope acceptance requires demonstrated label precedence and sticky admission, both authenticated gates, durable eight/three budgets, sequential child recovery and cancellation, all three configured check phases, stale-evidence refusal, failure visibility, exact-head delivery and confirmed closure.
- **d34** — Excluded work comprises #319, Implement enablement, feature story breakdown and mode handoffs, automatic detection, incident response, bulk repair, unrelated cleanup or redesign, destructive migrations, arbitrary-target delivery, general recursive or parallel children, and agent-authored check commands.


## Assumptions

- **a1** — Research observations remain tied to fb060b9c06ce923c47aa231b85975490200e2712; shaping inspected b95c12b155211cff0da15120ea150c74c53648c0, verified no relevant-area diff and observed the same research baseline at remote main, but executed no tests or live workflow probes.
- **a2** — #385 and its settled owner decisions override #367's illustrative graphs and reset language; d1–d6 preserve that scope, while d7 onward are shaping decisions proposed for review rather than findings or prior owner approvals.
- **a3** — A target-branch recipe file is the smallest project-owned configuration contract consistent with the ban on agent-written commands, so no separate recipe administration UI, dynamic selectors or command interpolation is included.
- **a4** — The existing main-only delivery call justifies the initial target restriction; changing the branch target is blocked rather than silently redirected.
- **a5** — Target-tip drift is checked before effects and after integration, but the existing merge API cannot atomically fence target movement during the request; observed drift after merge retains an integration exception and leaves closure pending rather than claiming tested-target delivery or attempting rollback.
- **a6** — Regression means a required configured phase plus retained mapping from success criteria to the fixer's regression tests; this version does not require automatically executing the new test against the pre-fix source.
- **a7** — Known flakiness never becomes a pass by rerunning the same binding, and infrastructure recovery may rerun invalidated checks without spending a repair slot only after the blocking cause is resolved and a fresh child generation is recorded.
- **a8** — An externally closed issue or unapproved external merge is reconciled and reported, but cannot substitute for the workflow's two owner gates; reopening completed issues, abandoning closed PRs and starting replacement workflows require separate operator action.

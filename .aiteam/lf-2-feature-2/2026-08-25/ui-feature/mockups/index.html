A UI for litefactory — five options

litefactory has real local state the forge never sees: eight tables, per-run JSONL event streams, worktrees, locks, watermarks, cost per run. Today the only way to read any of it is litefactory logs <issue>, which requires you to already know the issue number. There is no answer to “what is the factory doing right now”.

initialplan.md §15 puts “Web UI, dashboard, metrics endpoint” under deliberately not in v1 — worth knowing before picking one of these. The full argument, costs and open questions are in SPIKE.md; the ASCII versions of every screen are in MOCKUPS.md.

The options

A  ·  litefactory status — finish the CLI

The three commands §13 of the plan promised and that were never registered: status, runs, tail. Same tabwriter house style as repo list. Not really “a new UI” — but it is the missing half of the original design, and every option below needs exactly these queries.

cost S  ·  no new dependencies  ·  no new surface

See it →

B  ·  litefactory top — terminal UI

Full-screen master/detail with a live event stream, built on Bubble Tea. One binary, no port, nothing to secure, works over SSH to the Mac Mini today and the EPYC box later. What it cannot do is show you the plan you are being asked to approve — only tell you one exists.

cost M  ·  +bubbletea, lipgloss (pure Go, CGO_ENABLED=0 survives)

See it →

C  ·  litefactory serve — local web dashboard  recommended

Read-mostly HTML on 127.0.0.1:7457. Go stdlib only — net/http, html/template, embed, SSE for the live stream. No JS framework, no build step, still one binary. The only option that can put a rendered brief, a diff and a live run on the same page and give you a URL for it.

cost M–L  ·  adds a listening socket to a process holding your SSH key — loopback-only, enforced in config validation and checked by doctor, read-only in v1

Overview → One task →

D  ·  macOS menu bar item  rejected

Needs Swift or cgo bindings, which breaks CGO_ENABLED=0 and turns one static binary into a binary plus an app bundle plus a signing story. litefactory status --oneline piped into a status-bar tool you already run gets most of it for an afternoon.

cost L, and the wrong kind  ·  see MOCKUPS.md for the sketch

E  ·  the forge as the UI

Not new technology: a richer live status comment, and a pinned “factory status” issue the daemon keeps edited with every active session across every repo. Reuses internal/report wholesale — marker.go already solves find-my-comment-again, which is the hard part. Cheapest thing on the list, and the only one that works when you are not at the machine.

cost S  ·  complementary to any of A/B/C, not a substitute

Recommendation

A now, C next, E alongside. B only if a listening socket is a hard no. A is not optional — whatever gets built needs those queries, and building them behind a browser means testing them through a browser. C beats B on the moment that actually matters: a gate, where a brief or a plan is ready and you have to read it and decide. That is a reading task on a document with headings and links. The live stream — the part B would win on — is a thing you glance at, not a thing you study.

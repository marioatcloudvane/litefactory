# T-100.5 — Agent schedule proposals and ID-based decisions

> As an owner, I want an agent to suggest a concrete schedule that I explicitly approve so that large issues can be sequenced without giving the agent control.

This story introduces bounded proposal generation and a durable approval lifecycle.

## Why This Matters

Sequence advice is useful for complex work, but it must remain advice. The owner needs a clear identifier and immediate confirmation before any proposed work becomes active.

## Architecture Notes

- Define a vendor-neutral structured proposal-generator contract consumed by the daemon; do not model proposals as normal work runs.
- Validate every proposed item with the same factory rules as direct schedules before persistence.
- `--accept <id>` is atomic and owner/issue scoped; new proposals replace earlier pending ones and expiry is clock-driven.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | Propose produces an ID-bearing structured proposal or immediate failure, never active work. |
| AC-2 | Only the source owner on the source issue can accept/reject the stated pending ID. |
| AC-3 | Acceptance creates all items once, confirms IDs/count, and survives restart. |
| AC-4 | Agents cannot persist, accept, or dispatch schedules. |

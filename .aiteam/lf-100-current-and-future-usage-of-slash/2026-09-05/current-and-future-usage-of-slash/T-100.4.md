# T-100.4 — Due dispatch, dependency outcomes, and logging

> As an operator, I want due work to run safely and scheduling load to be visible so that queued work behaves predictably.

This story makes durable schedules eligible, dispatches them through normal capacity controls, and reports dependent failures.

## Why This Matters

Queued work must run no earlier than promised but must not overwhelm regular work. Failed prerequisites also need an explicit end state rather than silently waiting forever.

## Architecture Notes

- Extend the normal daemon tick; do not add timer goroutines or sleeps.
- Select/reserve due work in UTC-time then durable-ID order and use existing capacity/in-flight controls.
- Dispatch stored payload only; propagate failed prerequisite outcomes idempotently and add `scheduled` beside existing log fields.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | Work starts no earlier than due, on a later eligible poll subject to capacity, at most once. |
| AC-2 | Dependency delay begins after the last successful prerequisite and failure blocks dependents with a reply. |
| AC-3 | Logs expose outstanding pending work as `scheduled`, distinct from in-flight and deferred. |
| AC-4 | Scheduled payloads contain no scheduling metadata when delivered to agents. |

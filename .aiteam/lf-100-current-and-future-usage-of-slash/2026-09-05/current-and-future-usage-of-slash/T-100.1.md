# T-100.1 — Command boundary and schedule grammar

> As a repository owner, I want only meaningful commands and a clear scheduling syntax so that I can queue work without ambiguity.

This story removes unused commands and establishes validated factory-only scheduling input.

## Why This Matters

Owners currently see commands that do nothing. Scheduling adds time, timezone, dependency, and payload input that must be rejected safely rather than reaching an agent as ordinary prose.

## Architecture Notes

- Keep the existing first-token classifier; remove reserved unused vocabulary and classify `/schedule` separately from work commands.
- Add pure `internal/schedule` parsing/value types; inject receipt time and local location rather than reading time there.
- Reject nested scheduling, invalid duration/date/zone, DST folds/gaps, empty payloads, and incompatible flags as factory refusals.

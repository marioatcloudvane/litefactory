# T-100.6 — End-to-end deterministic verification

> As a maintainer, I want comprehensive deterministic coverage so that scheduling changes remain safe as the daemon evolves.

This story verifies scheduling across parsing, persistence, reporting, dispatch, and agent boundaries.

## Why This Matters

Scheduling combines durable state, timing, retries, and external reporting. A narrowly passing path is not enough when duplicate work or a stuck issue queue would be costly.

## Architecture Notes

- Use table-driven tests, real SQLite migrations/transactions, injected clocks, fake forge/agents, ticks, and daemon quiescence.
- Do not add live agent-process tests, sleeps, or a mocking framework.
- Assert public behavior and payload isolation plus unchanged normal command behavior.

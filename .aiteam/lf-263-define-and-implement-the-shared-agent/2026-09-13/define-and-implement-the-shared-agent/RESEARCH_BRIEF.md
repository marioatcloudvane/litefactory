## Proposed field schema (common grouping agreed; remaining semantics provisional)

| Location | Ownership, type and rule |
|---|---|
| `meta` | Factory-authored object in assembled snapshots/read responses. Reject it in agent submissions. Not a signature: authorization comes from the bound broker request. |
| `meta.schema_version` | Application shape version, initially `"0.1-draft"`. Version is deliberately separate from workflow and existing submission contract. Production numbering to be agreed. |
| `meta.operation` | Proposed message-family discriminator: `work`, `classify`, `schedule_proposal`, `conflict_proposal`, or advisory `progress`. Useful only if these share an envelope; redundant for a work-only endpoint. Operations are not new modes. |
| `meta.task`, `run_id`, `attempt_id`, `mode` | Trusted normal-work attribution. Mode is one of five canonical values. `attempt_id` is a non-secret display identity, not the capability. Auxiliary operations use an invocation ID and omit inapplicable task/run/mode fields. |
| `meta.workflow_version`, `submission_contract_version` | Trusted versions from existing persisted scope where applicable: workflow selects lifecycle policy; submission contract selects existing contribution/receipt rules. Neither is the proposed envelope schema version. Values 2 are illustrative; unmanaged Research need not have these fields. |
| `meta.result_id`, `result_revision` | Logical mutable result identity and monotonically increasing snapshot revision, allocated by factory. Scope a result to one mode and authorized work context; never silently carry authority across attempts. |
| `meta.scope_ref`, `request_id` | Trusted frozen/baseline reference and request correlation. Resolved scope contains authoritative story IDs, generation, exact source revisions, roles, dependencies and retained proof. A reference avoids echoing the whole scope on every submission. |
| `result.outcome` | Agent claim `completed`, `incomplete`, `blocked`. No `accepted` or `published`. `reason` required and nonblank for incomplete/blocked, absent for completed. Run process failure can occur with or without any result. |
| `result.comment` | Nonblank owner-facing Markdown. Factory renders structured questions once, redacts, bounds and publishes; this field grants no external-write authority. |
| `result.questions` | Optional ordered list; omit when there are no questions. Nonempty only for authorized Research/Plan exits. Item: stable `id`, nonblank `text`, optional options with stable IDs/label/description and optional recommended option ID. Nonempty questions imply incomplete/blocked. Owner answers arrive via the existing authenticated continuation, not agent-writable answer/approval state. |
| `result.recommendation` | Optional common `{text, action?}`. Nonblank human-readable text; optional allowlisted action token, initially illustrative `action.moveto.planmode`. Omit action when no machine-readable proposal exists; no null or free-form executable command. Advisory only, independent of outcome and factory authorization; never performs a transition. |
| `result.artifacts` | Optional ordered `{id,kind,path,description?}` references; omit when none. Repository-relative path; root/symlink/size checks remain necessary. Factory may retain content hashes and storage references separately. A mutable path alone is not evidence. An explicit empty list is allowed where clearing is permitted; Validate has no artifact requirement. |
| `result.payload` | Exactly one active mode object, validated against trusted mode. Never require agents to echo inactive null payloads. |
| `payload.research` | Request, findings with stable IDs and source evidence, decisions/assumptions with stable IDs. Recommendation is common. Partial findings retained on incomplete/blocked. |
| `payload.plan` | For completion: current typed `summary` and full `stories`. For incomplete/blocked: optional draft `stories` and optional context; a proposed extension beyond current context-only discussion. Keep common questions in one place. Never publish provisional stories; see run 0004. |
| `payload.implement` | Authorized per-story contributions: engineering_complete/blocked/invalidated for separated; verified/blocked/invalidated for legacy. Evidence/capture as existing v2. Common incomplete outcome preserves finished siblings; no aggregate completion inference. |
| `payload.validate` | Authorized stories, snapshot and full criteria/review findings; names/IDs and evidence semantics match v2. Missing retained proof uses unverified findings, possibly empty snapshot ID as current validator allows. No new checks/captures. |
| `payload.spike` | Request, work_done, findings, decisions, not_done. Recommendation is common. Completed investigation may recommend larger work. |

Unknown, duplicate, null, trailing and wrong-type fields should reject under the strict application decoder. Optional common/narrative collections may be absent; do not require empty filler. Current completed typed Plan still requires its domain collections, using `[]` only where allowed. Draft Plan fields are conditional as described in run 0004. Inactive fields reject. Enforce UTF-8 byte/rendered output budgets separately from character counts; reuse current stage limits before selecting new aggregate budgets. A future executable JSON Schema can validate structure but cannot prove scope authority, graph validity, byte budgets, retained checks or absence of duplicate raw JSON keys after ordinary parsing.

## Creation and revision-checked sparse changes

Recommendation: **explicit domain operations targeting stable IDs**. Creation supplies a result valid for its outcome: an incomplete Plan may contain rough draft stories. Completion requires full semantic content. Update supplies `result_id`, `expected_revision`, and operations; these are untrusted selectors/preconditions, not assignments to `meta`. Factory checks current attempt, target ownership and allowed domain edits.

Use a deliberately small operation set: `replace` for a permitted scalar/object field, `add_item`, `update_item`, `remove_item` for an authorized collection, and `reorder_items` with the exact complete ordered ID list. Paths are relative to result. No array-index targeting. Stories use existing `key`; tasks/criteria/questions/artifacts use `id`; assessment entries use existing `name`. Reject missing/duplicate IDs and wrong operation/collection combinations. Newly introduced narrative lists can gain IDs; untouched existing arrays may be replaced as whole fields until such a need exists. Do not silently regenerate IDs on reorder.

Omitted changes preserve current values. `null` is rejected, never a deletion shortcut. Explicit `remove_item` deletes only a mutable draft item; references must be repaired in the same transaction. Removal of approved obligations is not a result edit: factory-mediated replanning and the existing criterion retirement rules apply. Removing an item does not erase its prior snapshot/history. Add without positioning appends; optional `after_id` positions relative to an existing item; reordering must name every surviving item exactly once.

Load a single base revision, authorize and apply all operations in order to a private copy, validate the **complete merged result**, then atomically store a new full snapshot and advance the latest pointer only if the revision still matches. No partial updates. The exchange sample modifies a comment and F-1 while preserving artifacts/decisions and absent questions. A stale base rejects with expected/current revision and scoped reread guidance; no automatic blind rebase. Validate dependencies, cycles, roles, references, criterion coverage, rendered budgets and retained evidence on the merged object, not merely the supplied fragment.

Alternative: JSON merge-patch is smaller for nested scalar objects, but arrays normally need replacement or a map-plus-order redesign, and null-as-delete creates ambiguity. The explicit operation proposal is easier to inspect for story edits, deletion and ordering. This is a design recommendation, not an implemented protocol or a claim about token savings.

## History, correlation and authority

Keep mutable result snapshots distinct from immutable **engineering snapshots**. The former preserve all authored results/revisions; the latter preserve exact implementation bytes and executed evidence. Changes to commentary do not rewrite an earlier run report, captured proof, submission payload, decision or frozen story scope. New attempts get new authority even if they are permitted to update a continuing logical result. Whether results are per run or span a same-mode continuation remains an owner-review choice; recommend logical same-mode results with every revision retaining its originating run/attempt.

Reuse v2 request journaling: identical retry bytes reuse the request/receipt; corrected bytes get new correlation. Check idempotent replay before treating its already-applied revision as stale. Persist the update and its durable receipt consistently so lost responses cannot apply an update twice. Reject reuse of correlation with different content or wrong attempt; reject unsupported versions explicitly, never infer an upgrade from a payload. Provider resume identity, run ID, attempt, request ID, application schema version, result revision, submission version and workflow version are separate concepts.

Do not compress feedback to one status. **Received** means input arrived/durable correlation exists; **valid** means schema and semantics passed; **snapshot recorded** means authored result/evidence retained; **accepted** is a separate domain decision; **published** means confirmed external effect. The current receipt already has engineering/acceptance/effect/Plan dimensions; extend it rather than replace those with a misleading success flag. Preserve pending/failed/retry effects and immutable observations of later receipt states. A no-result/timeout/abandoned/quota-interrupted process has a factory execution report even if it never authored JSON.

## Advisory in-flight progress (new)

Use a tiny separately validated action: sequence, topic and message. Factory binds run/attempt and receive time; no claimed terminal outcome, readiness, percent-complete authority or acceptance. Sequence is strictly increasing within an attempt, scoped independently from contribution sequence. Exact duplicate sequence/content is idempotent; same sequence/different content conflicts; late older updates cannot overwrite the displayed latest value. Gaps are permitted for lossy advisory delivery. Reject inactive/foreign attempts.

Proposed initial policy for review: message ≤2 KiB UTF-8, at most 32 topics per attempt; retain latest update per topic plus last 100 accepted messages until normal run-log retention expires; coalesce display updates to at most one per topic per five seconds. Disclose dropping/coalescing; do not promise replay beyond retention. Factory owns the clock and retention. These numbers are draft choices, not measured requirements. Progress must never trigger story closure, dependency release, readiness or acceptance, and cannot substitute for current engineering evidence submissions. No MCP dependency is needed to define it.

## Shared library and instructions, retained for later

The reusable library should centralize strict decoding, discriminated shapes, stable diagnostics, scoped baseline reads, complete-result validation, authorized operations, revision checks and snapshot construction. Reuse `internal/agent` contribution semantics and the typed Plan validator rather than inventing a parallel workflow. Persistence stays in `internal/store`; lifecycle/effects stay with factory owners; provider adapters only translate transport. Public module versus an internal package is not settled by this draft.

A future shared finalization skill should provide early discovery of operation/version/ownership, evidence-capture requirements, scoped baseline access and required exits. Load detailed mode serialization just before submission; incomplete/blocked/question exits must use the same path. Keep work constraints and evidence requirements available before engineering/tests, not deferred until finalization. No agent-authored completion can bypass factory lifecycle gates.

# US-5 — Report story progress and close verified work

> As the owner, I want each story closed immediately when its own implementation is verified so that I see progress while other stories and the parent run remain active.

Publish story milestones and close each story immediately after its own acceptance, review and testing evidence is accepted. Final parent validation, process exit, saving, pushing and merge are not prerequisites.

## Why This Matters
The parent run alone does not show which stories succeeded. Story-level updates make partial results visible, but a successful agent exit is insufficient evidence to close work. Reporting failures must be recoverable without repeating already completed implementation.

## Architecture Notes
- **T-5.1 — Define structured story evidence and persist execution attempts:** internal/agent; internal/store; dependencies: T-3.1, T-4.1. Strict versioned incremental outcome contract identifies selected story/revision, attempt, event sequence, AC evidence, implementation digest and story-scoped review/tests. Persist accepted evidence, superseding invalidation and ordered milestone intents independently of subprocess completion. Identical replay is idempotent; conflicting duplicates cannot verify.
- **T-5.2 — Add completion and invalidation state updates to GitHub adapter:** internal/github; dependencies: T-1.3. Add issue close with completed reason and reopen for invalidated completion via the existing client; check responses, errors and rate-limit classification. Targets come from managed identities. Native lock/unlock remains excluded; reopening corrects completion without changing frozen scope.
- **T-5.3 — Validate evidence and emit story milestones:** internal/turn progress service; internal/daemon tick scheduling; internal/report; both implementation orchestrator copies; dependencies: T-5.1, T-4.2. Consume incremental events during the active run; validate known identities, sequence, selected revision and named AC/review/test evidence against a stable implementation snapshot. Persist verification and immediately attempt completion reporting/close, without final harvest or push. A raw DONE or absent required scoped checks leaves the story open. Later unrelated failures retain closures; invalidating evidence revokes only affected completions. Distinguish launch-admitted started notice from proven running process. Update both instruction copies and relevant current context/user documentation for immediate closure, pending parent checks/save/push, and invalidation/reopening.
- **T-5.4 — Reconcile completion reporting and closure without reexecution:** internal/turn reporting; internal/daemon pending work scheduling; internal/store; dependencies: T-5.2, T-5.3, T-1.1. Completion comment precedes immediate close; completed state follows both. Retry from durable evidence during or after the active run. Serialize effects per story with monotonic completion/invalidation versions; supersede stale pending close, reconcile uncertain in-flight close, then report invalidation and reopen. Human closure alone never verifies; API failure never triggers reimplementation.
- **T-5.5 — Test malformed evidence and successful/partial story outcomes:** internal/agent; internal/github; internal/report; internal/turn fixtures; dependencies: T-5.1, T-5.2, T-5.3. Hold the fake parent runner and a sibling story active with channels; submit valid scoped evidence and prove completion report/close precede their release and any save/push. Cover raw DONE, missing checks, malformed identities, changing evidence, replay/conflicting duplicates, partial success, unrelated later gate/process/push failure and affected-story invalidation. Use real git fixtures and no sleeps.
- **T-5.6 — Test milestone/closure recovery and workflow parity:** internal/store; internal/daemon and turn fixtures; dependencies: T-5.4, T-3.3, T-4.3. Real SQLite and httptest exercise live report/close failure, acknowledgement loss, close success before local persistence, restart and reopen failure. Exercise invalidation overtaking queued or uncertain close; only the newest desired state may settle. Assert no repeat implementation, no stale reclose and no lost refusal on completed or reopened-frozen children. Extend fixtures through new Plan publication → child refinement → freeze → resume → live verification/close before parent exit → affected invalidation/reopen with both fake runners and no tracked story transport. No legacy migration fixtures or legacy-file cleanup assertions.
- Run 0003 decision: finished means verified story-scoped implementation. Reports identify the validated snapshot and disclose pending parent checks/save/push. Evidence validation checks structured agent reports and artifacts; it is not an independent proof of correctness. Unrelated later failures preserve closures; invalidated completions reopen visibly with scope still frozen.

- Live transport and validation ownership follow ARCH_REVIEW.md, “Active-Run Completion Contract”: atomically published per-run event records are consumed by the turn progress service from daemon ticks even while the sole execution slot is occupied. The orchestrator coordinates stable scoped review/test evidence; final harvest drains before deleting transport. This changes progress observation without adding another agent run or goroutine.

## Acceptance Criteria
| ID | Criterion |
|----|-----------|
| AC-5.1 | Each selected story has a durable attempt and frozen/started/blocked-or-failed/completed milestone containing parent/run and revision references; started explicitly means admitted for launch. |
| AC-5.2 | Incremental outcomes during the active run bind selected story/revision, attempt and monotonic event identity to AC/review/test evidence; raw DONE, missing checks, unknown identities and conflicting duplicates cannot authorize closure. Identical replay is idempotent. |
| AC-5.3 | Verification requires safe immutable evidence references, implementation content digest and passing required story-scoped acceptance/review/tests. A changed or unstable validation basis stays open; subprocess exit, aggregate gates, save/push and merge are not prerequisites. |
| AC-5.4 | With parent runner and a sibling held active, valid story evidence causes its report and GitHub close before either finishes or save/push starts. An unrelated later aggregate, subprocess or push failure does not reopen it; incomplete siblings remain open with explanations. |
| AC-5.5 | Immediately after verification is durably accepted, post completion evidence and close with completed reason; completed is recorded only after both succeed. The report identifies the validated implementation and any pending parent validation/save/push. |
| AC-5.6 | Report/close/reopen failures and ambiguous responses remain durable pending work recoverable during the run or after restart without another implementation run; successful remote mutation before local persistence is recoverable. |
| AC-5.7 | Later evidence invalidating acceptance or implementation revokes only affected completions, posts a linked reason and reopens those children while retaining frozen scope. Ordered effect versions prevent an obsolete queued or uncertain close from overriding invalidation; recovery tests cover this race and both fake runners. The new-workflow fixture spans Plan publication, child refinement, freeze, resume, live closure and invalidation for both runners; relevant documentation uses the same completion policy. |

# US-001 — Continuous and bounded issue log following

> As an issue observer, I want one log follower to continue through later runs and finish safely when no further run arrives, so that it stays useful without silently waiting forever.

Deliver issue-level rollover, explicit-run pinning, terminal database handling, and their regression coverage as one observable follow lifecycle.

## Why This Matters

Today a follower can look healthy while it is fixed to an old run and misses all later work. It can also wait indefinitely when a writer is interrupted without recording its final event. The difficult part is preserving every final log byte while making the transition between runs unmistakable and keeping raw output machine-readable.

## Architecture Notes

- Evolve the existing logs command into an outer issue-follow coordinator plus one shared per-run follower; retain the direct-file, ticker-driven command flow.
- Keep lifecycle policy and output routing in `internal/cli`; consume ordinal-ordered store accessors and the persisted agent's validated timeout configuration without adding SQL, interfaces, or fallback agent selection.
- The per-run follower covers absent active log files, retained-handle drains, all terminal-event recognition, refreshed database status, exactly one final drain, and partial-tail flushing. The outer coordinator alone discovers later ordinals.
- Carry command context through observations and waits; cancellation exits immediately. Unexpected store/file/configuration failures wrap their cause and return non-zero.
- Risk: terminal database state may race with final file writes; the final drain must occur before explicit exit or issue-level successor waiting.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-001.1 | `logs -f <issue>` initially follows the newest resolved-session run and subsequently follows every higher ordinal in ascending order; `logs -f <issue> --run N` never emits or opens a later ordinal. |
| AC-001.2 | Before each subsequently entered ordinal, rendered follow emits an unfiltered visible zero-padded ordinal separator to stdout; raw follow emits that separator only to stderr and leaves stdout equal to the concatenated source JSONL bytes. |
| AC-001.3 | A completed implicit-follow run waits at most that run's recorded agent timeout for its earliest higher ordinal, follows one created before the deadline, and otherwise exits successfully. |
| AC-001.4 | An unavailable or unrecognized persisted run agent produces an actionable non-zero configuration error rather than selecting another timeout. |
| AC-001.5 | During active following, status refreshes do not keep a store connection open; a database-terminal status triggers exactly one final log drain before explicit exit or implicit successor waiting. |
| AC-001.6 | A follower that has already reached EOF exits after each newline-terminated `result`, `turn.completed`, and `turn.failed` event is appended; cover raw and rendered paths where they differ. |
| AC-001.7 | A database-terminal run with no terminal event exits when explicitly pinned and enters bounded successor waiting when implicitly selected; a complete final event is retained and a partial tail flushes only once terminality is known. |
| AC-001.8 | Tests cover multi-ordinal rollover, a later allocated run lacking its log file, separator immunity to `--only`, grep, case-insensitive, and invert filters, successor-timeout expiry, and immediate successful cancellation. |

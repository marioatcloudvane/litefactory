# US-18 — Root-file composition for harnesses that use one shared agent file

> As a platform operator using a harness that reads all its agent instructions from a single root
> file (like `AGENTS.md` or `CLAUDE.md`), I want each installed team's agents to appear there as
> their own clearly-marked section, so that installing or updating a team doesn't clobber
> hand-written content elsewhere in that same file.

Delivers marker-tagged section composition: renderers that target a root file (Claude, opencode)
write their output as a `BEGIN`/`END`-delimited block inside that file, upserted in place, leaving
everything outside the markers untouched.

## Why This Matters

Some harnesses don't read a directory of per-agent files — they read one file, top to bottom.
Writing a team's agents into a file like that can't mean "overwrite the whole file," because an
operator's own notes or other tools' output are likely to already be in it, and it can't mean
"append forever," because updates and removals would leave stale content behind indefinitely. This
story is the mechanism that lets litefactory own a clearly-bounded piece of a file that isn't
otherwise its own — a common shape across two of the three renderers (US-6 Claude, US-8 opencode),
built once here instead of twice.

## Architecture Notes

- **Marker format:** `<!-- litefactory:team BEGIN team=<team> agent=<agent-key> -->` … `<!-- litefactory:team END -->`, one such pair per agent per contributing team. A `shared` agent referenced by more than one installed team gets one deduplicated block, not one per team — the block's opening marker lists every contributing team as a comma-separated `team=` value (e.g. `team=go-team,other-team`) rather than repeating the agent's body once per team.
- **Upsert algorithm:** on write, locate an existing marker pair for that exact `agent`+contributing-team-set combination; if found, replace the span between and including both markers in place; if not found, append a new pair at the end of the file. Content outside any marker pair is never read for meaning and never modified — this is what protects hand-written content elsewhere in the same root file.
- **Removal:** when an agent is dropped from every team that used to contribute to its block (via an index edit, or losing the last contributing team), the next `team update` (US-11) removes that marker pair entirely rather than leaving an orphaned empty block.
- **Drift detection, reusing US-10's philosophy rather than inventing a second one:** the marker-tagged span is treated as a "virtual file" for US-10's five-state classification — its `sourceHash`/`renderedHash` in the US-9 lockfile are computed over just the bytes between (and including) its own markers, not the whole root file. A hand-edit inside a team's markers is Locally-modified exactly as a hand-edit to a standalone file would be; a hand-edit elsewhere in the same root file is invisible to litefactory, by design, since that content was never in scope.
- **Consumers:** US-6 (Claude) and US-8 (opencode) both target root-file composition for at least part of their output and depend on this story for the shape of `RenderedFile` that names a root file plus a marker-section identity rather than a standalone path. US-7 (Codex) has no root-file equivalent and does not depend on this story — documented in US-7 itself as a deliberate asymmetry, not revisited here.
- This story owns the upsert/removal mechanics and the virtual-file hashing scheme; it does not own what content goes inside a block — that's each renderer's (US-6/US-8) own output.

| AC-3 | Removing an agent's last contributing team removes its marker pair entirely on the next `team update`, leaving no orphaned block. |

# US-18 — Root-file composition (marker-tagged sections in AGENTS.md / CLAUDE.md)

> **PLACEHOLDER (2026-09-05).** This is a new story added by the 2026-09-05 narrow reconciliation
> pass, identified as a consequence of the corrected design (JSON as a pure index of markdown
> files) rather than as one of the sponsor's five numbered refinements directly — several existing
> stories (US-6, US-7, US-8, US-9) now reference it as a dependency once the design correction made
> clear that per-harness rendering also has to compose into shared root files (`AGENTS.md`,
> `CLAUDE.md`) rather than only writing standalone per-agent files. Full task breakdown,
> architecture notes, and acceptance criteria are **deferred to the follow-up planning pass** —
> this file exists only to hold the story's place in `plan_brief.md`'s Story Index and to record
> its scope and dependency now, before that detail is written.

> As a platform operator, I want litefactory to compose its own generated content into a clearly
> marked section of my repo's existing `AGENTS.md` / `CLAUDE.md`, so that a file that already has
> hand-written content of mine isn't overwritten wholesale just because part of it is now
> litefactory-managed.

**Scope (one line):** define and implement marker-tagged section composition — inserting,
replacing, and detecting litefactory-owned content within a subsection of a root file that the
operator otherwise owns and edits freely outside those markers.

**Depends on:** US-5 (the per-harness renderer contract) — root-file composition is consumed by
individual renderers as an additional output shape alongside their existing standalone-file
output, so the renderer contract must exist first.

**Known open questions for the follow-up pass** (not resolved here): the exact marker syntax and
whether it differs per harness; what happens when the markers exist but their content was
hand-edited between litefactory's own opening and closing tags; whether this applies to every
harness's root file or only some.

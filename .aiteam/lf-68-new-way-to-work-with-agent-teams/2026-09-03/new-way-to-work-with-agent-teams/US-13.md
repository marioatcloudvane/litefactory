# US-13 — `team manage` per-repo agent source override

> As a platform operator, I want to point one agent, in one repo, at a local markdown file instead
> of whatever the team index says, so that I can patch or customize a single agent for this repo
> without forking the whole team definition or waiting on an upstream change.

Delivers `team manage`, resolving Open Question 6 (the research brief's biggest unresolved judgment
call) with a concrete mechanism: a per-repo, per-agent-key source override recorded alongside the
lockfile, consumed at render time in place of whatever the active index source would otherwise
resolve for that key.

## Why This Matters

Not every fix belongs upstream immediately: an operator may need to tweak one agent's wording or
tool list for one specific repo today, without touching the shared team definition everyone else
uses. Without some override mechanism, the only paths available are hand-editing the rendered
output (which `team update` will then treat as a conflict forever) or forking the entire index just
to change one file. This story's job was explicitly to pick one of three shapes the research left
open and defend the choice, rather than leave it a question for whoever implements this later —
that decision, and the reasoning behind it, is recorded here.

## Architecture Notes

- **Open Question 6, resolved.** Three candidates were on the table:
  - (a) point a key at a different local markdown file for this repo only;
  - (b) an include/exclude toggle for a specific key within an installed team;
  - (c) drop the command entirely.

  **Decision: (a).** Reasoning: (b) adds no real capability — removing an agent from a team is
  already possible by editing that team's `agents` array in whichever index is active (US-2), so a
  toggle would just duplicate an existing lever at a different location. (c) forecloses a real,
  recurring need — patching one agent for one repo without forking the whole index or waiting on an
  upstream review — for no offsetting simplification, since this story is small regardless. (a) adds
  genuine new capability at the finest available grain (one key, one repo), and reuses the existing
  `{source, dest}` shape from `AgentEntry` (US-1), so it composes with rendering (US-5) without a
  new concept. This is a headless-run assumption, not sponsor-confirmed; flagged here for review.
- Mechanism: `team manage <agent-key> set source=<local-path>` records `{agentKey, source}` in a new
  per-repo overrides file, `.litefactory/team.overrides.json` (same bookkeeping directory US-9
  introduces). `local-path` is resolved relative to the target repo root and validated to exist and
  be a markdown file at write time.
- At render time (US-5, invoked via US-9/US-11), an override for a given agent key supersedes
  whatever `AgentEntry.Source` the active index would otherwise resolve for that key — `Dest` is
  unaffected; only the source markdown changes. This is the one place in the whole feature where a
  single field of an otherwise index-resolved agent is replaced without replacing the team or index
  wholesale — deliberately narrow, and confined to this file, not folded into US-2's source
  resolution (which stays a three-tier index-level choice, never per-agent).
- `team manage <agent-key> unset` removes the override, reverting to the index-resolved source.
- `team manage <agent-key> show` reports whether an override is active and, if so, its local path.
- Interaction with US-9/US-10/US-11: an overridden agent's `sourceHash` (in the lockfile) is
  computed from the override's local file, not the index source — from US-10's perspective an
  override is indistinguishable from "the source changed"; classification logic needs no special
  case, it already reacts to `sourceHash` correctly regardless of which file produced it.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | `team manage <agent-key> set source=<path>` records an override that is honored by every subsequent render, add, and update for that repo and that key only. |
| AC-2 | `team manage <agent-key> unset` removes the override; the next render uses the index-resolved source again. |
| AC-3 | `team status`/`team update` classify drift for an overridden agent against the override's local file, with no special-cased behavior required in US-10's classification logic. |
| AC-4 | A `set` command naming a local path that doesn't exist, or isn't a markdown file, fails with a precondition error and records no override. |

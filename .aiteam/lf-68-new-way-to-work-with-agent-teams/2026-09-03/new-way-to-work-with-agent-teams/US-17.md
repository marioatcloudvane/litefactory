# US-17 — Bootstrap a `go-team` index from litefactory's own agents

> As a platform operator setting up litefactory's own agent team on a new repo, I want a ready-made
> `go-team` entry in the shipped index, built from the real agents this project already uses, so
> that I don't have to hand-assemble the first team definition myself before I can use any of this
> feature.

Delivers the embedded default index's `go-team` entry: a concrete, worked JSON example naming every
one of litefactory's 13 real agents, split between `go-team`'s own inline `agents` map and the
implicitly-shared top-level `shared` map (US-2).

## Why This Matters

Every other story in this feature builds the machinery to install and maintain a team — none of them
give an operator anything to install on day one. Without a real, working example baked into the
default index, the first thing anyone does with this feature is write a JSON file by hand from
scratch, which is exactly the friction this feature exists to remove. This story makes the shipped
default useful immediately, using litefactory's own agent roster as the worked example, and settles
which of those agents are Go-specific versus generally useful — a question the research left open.

## Architecture Notes

- **Roster, confirmed against this repo's actual agent definitions:** 5 Go-specialist agents
  (`go-architect`, `go-implementation-engineer`, `go-code-reviewer`, `go-unit-test-engineer`,
  `go-integration-test-engineer`) and 8 generic/orchestration agents (`codebase-tour`,
  `web-researcher`, `requirements-engineer`, `proxy-product-owner`, `app-context-updater`,
  `research-orchestrator`, `plan-orchestrator`, `implement-orchestrator`) — 13 total. Tooling entries
  that appear in the same agent listing but are not part of litefactory's own team roster (`claude`,
  `Explore`, `general-purpose`, `Plan`, `statusline-setup`) are excluded from this story's index
  entirely — they are host-level utilities, not agents this feature installs into a repo.
- **Open Question 15, resolved: yes, all 8 generic/orchestration agents go in `shared`.** None of them
  are Go-specific in what they do (requirements gathering, orchestration, codebase touring, web
  research, context bookkeeping), so every one of them is exactly as useful to a future non-Go team as
  to `go-team`. Splitting them across multiple named maps per team would just duplicate the same
  eight entries anywhere else this pattern is reused; `shared`'s implicit-availability semantics
  (US-2) exist precisely so this doesn't need duplicating. Only the 5 Go-specialist agents are named
  directly, inline, under `go-team`'s own `agents` map.
- **Bootstrap step, distinct from the index's own `source`/`dest` fields:** each of these 13 agents
  already exists today at `.claude/agents/<key>.md` in this repo. Building this story's worked
  example means first copying each file from that current location to its new home under `teams/` —
  `teams/go-team/<key>.md` for the 5 go-specialist agents, `teams/shared/<key>.md` for the 8 shared
  ones. This is a one-time authoring move, not a schema field; it happens once, before the index
  below is written, and does not recur at load or render time.
- Once a file is at its new `teams/` location, the index's `source` for that key is that new path
  (e.g. `teams/go-team/go-architect.md`), relative to this repo's own root — per US-1/US-2's
  schema-level meaning, `source` is where the markdown lives in the already-built `teams/` layout,
  never the pre-migration `.claude/agents/` path. `dest` is the harness-neutral installed filename
  the entry renders to (e.g. `go-architect.md`), matching the filename the source file already uses.
  This story is index construction, not content authoring; beyond the one-time copy above, it does
  not create or edit any agent's markdown body.

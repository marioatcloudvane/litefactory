# US-10 — `team status` drift detection

> As a platform operator, I want to ask whether the agent files installed in a repo still match
> what litefactory would install today, and — if not — whether that's because I edited a file by
> hand or because the team definition changed upstream, so that I know whether it's safe to update.

Delivers `team status`'s classification of every installed file into one of five states, replacing
the rejected nine-row three-hash drift table with a byte-comparison scheme built on US-9's
provenance markers. Also absorbs the still-relevant concern from the dropped US-12: telling an
externally-modified installed file apart from a normal upstream change was US-12's whole scope, and
that distinction is now just two of this story's five states, not a separate command.

## Why This Matters

Once a team is installed, both sides of it can move: someone can hand-edit a generated file to fix
something quickly, and the team definition upstream can also change independently. Before this
story, there was no way to tell those two situations apart short of reading the files yourself.
Collapsing that into a five-way answer — untouched, hand-edited, upstream moved on, both changed, or
gone missing — is what makes a later `team update` (US-11) safe to trust: it can update the cases
that are unambiguous and refuse the ones that would silently discard someone's edit.

## Architecture Notes

- Replaces `plan_brief.md` Shared Decision 1's nine-row three-hash classification table entirely.
  The new scheme uses US-9's two-hash lockfile record (`sourceHash`, `renderedHash`) plus one fresh
  computation done at `status` time — a re-render of the agent's *current* source — and classifies
  by byte comparison, not by a merged-config diff:

  | State | Condition |
  |---|---|
  | In sync | installed file bytes == fresh render of current source |
  | Locally modified | installed file bytes != fresh render; current source hash == lockfile's recorded `sourceHash` (source hasn't moved; the difference is a hand-edit) |
  | Upstream updated | installed file bytes == lockfile's recorded `renderedHash` (untouched since install); current source hash != recorded `sourceHash` (safe, non-conflicting update available) |
  | Conflict | installed file bytes match neither the fresh render nor the recorded `renderedHash`, and current source hash != recorded `sourceHash` (both sides changed) |
  | Missing | lockfile has a record for this file but the file is absent from disk |

  Five states, not nine — the three-hash model's finer distinctions (e.g. separating "cosmetic
  re-render" from "semantic source change") had no reader that used them; this table keeps exactly
  the distinctions US-11 needs to decide what's safe to touch.
- No new hash type is introduced beyond US-9's `sourceHash`/`renderedHash`; classification is a
  read-only comparison, never a write, and never mutates the lockfile.
- `team status`'s report names, per file: its classification, the agent key, the harness, and (for
  Locally modified / Conflict) that a hand-edit is at risk of being discarded by `team update`.
- T-21 (classification logic) is the task US-4's CLI scaffold (T-25) and US-11 (T-11.x) both depend
  on — it is this story's load-bearing task, not the CLI presentation around it.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | Every installed file tracked by the lockfile is classified into exactly one of the five states, using only byte comparison and the lockfile's recorded hashes — no merged-config diff of any kind. |
| AC-2 | A file classified Locally modified or Conflict is reported with an explicit note that `team update` would risk discarding a hand-edit. |
| AC-3 | A lockfile record whose file is absent from disk is classified Missing, not silently skipped from the report. |

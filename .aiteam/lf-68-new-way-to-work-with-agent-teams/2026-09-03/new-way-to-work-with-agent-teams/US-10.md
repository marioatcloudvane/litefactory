> As a platform operator, I want `litefactory team status` to tell me exactly which generated
> files have been hand-edited, are missing, or are stale against the definition they came from,
> so that I know what an update would touch before I run it.

This story implements the drift-classification logic and the read-only `team status` command
built on top of it.

## Why This Matters

Once a team's files are generated, someone will eventually hand-edit one — deliberately, to fix
something locally — and litefactory has to be able to tell that apart from a file that's simply
gone stale, or one that was never its file to begin with. This is the piece the original research
flagged as needing real design work rather than a quick guess, because getting it wrong in either
direction is bad: too aggressive and a hand-edit gets silently discarded later; too conservative
and `team update` becomes useless because everything looks "modified." This story is where that
design turns into working classification logic, covering nine distinct on-disk situations, not
just the obvious "changed or not."

## Architecture Notes

- The full nine-row decision table (state × source-changed → classification) lives in
  `plan_brief.md`'s Shared Decisions §1 — implement directly against that table; it is this
  story's specification, not a summary of it.
- `foreign` (an extra file with no litefactory provenance marker) counts as a real, reportable
  finding for exit-code purposes — it is not treated as noise to be ignored.
- This story's classification logic (T-21) must land before US-4's CLI scaffold (T-25), since the
  scaffold's error/exit-code translation depends on it; this story's own CLI wiring (T-29) lands
  after T-25.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | A fresh install reports every artifact clean, and `team status` exits 0. |
| AC-2 | Editing one generated file by a single byte reports exactly that file `modified`, every other artifact clean, and a non-zero exit code. |
| AC-3 | Deleting one generated file reports it `missing`. |
| AC-4 | An extra file at an owned path with no lockfile entry is reported as `orphan` (carries the litefactory provenance marker) or `foreign` (does not). |
| AC-5 | A corrupt lockfile causes `team status` to fail without rewriting anything. |

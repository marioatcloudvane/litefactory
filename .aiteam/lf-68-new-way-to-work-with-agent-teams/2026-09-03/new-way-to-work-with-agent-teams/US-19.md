# US-19 — Fuzzy repo resolution for `team add <repo-identifier> <team>`

> **PLACEHOLDER (2026-09-05).** This is a new story added by the 2026-09-05 narrow reconciliation
> pass, identified as a consequence of the corrected design rather than as one of the sponsor's
> five numbered refinements directly — once the index can point at teams sourced from a registered
> external repo (not only the embedded default), `team add` needs a way to resolve which registered
> repo an operator meant from a short or partial identifier. Full task breakdown, architecture
> notes, and acceptance criteria are **deferred to the follow-up planning pass** — this file exists
> only to hold the story's place in `plan_brief.md`'s Story Index and to record its scope and
> dependency now, before that detail is written.

> As a platform operator, I want `litefactory team add <repo-identifier> <team>` to resolve a
> short or partial repo identifier to the correct registered repo, so that I don't have to type or
> remember a full repo path or URL every time I add a team from somewhere other than the embedded
> default.

**Scope (one line):** add fuzzy/partial-match resolution of a repo identifier argument to
`team add`, against whatever set of registered external repos exists at that point in the design,
with a clear, non-silent failure when the match is ambiguous.

**Depends on:** US-4 (the CLI scaffold) — this story extends `team add`'s argument parsing, which
lives on top of the scaffold US-4 provides.

**Known open questions for the follow-up pass** (not resolved here): what "registered repo" means
concretely under the corrected design (is there a registry file, and if so who writes it); the
exact matching algorithm (prefix, substring, Levenshtein-style fuzzy) and its ambiguity threshold;
whether an ambiguous match lists candidates or simply errors.

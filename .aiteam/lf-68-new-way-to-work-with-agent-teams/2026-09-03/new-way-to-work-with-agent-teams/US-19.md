# US-19 — Fuzzy repo resolution for `team add <repo-identifier> <team>`

> As a platform operator, I want to name the repo I mean by typing roughly its name, not its exact
> `owner/name` slug, when I run `team add`, so that the common case is a short command and the tool
> only asks me to be precise when it genuinely can't tell which repo I mean.

Delivers `<repo-identifier>` resolution: exact `owner/name` matching when the identifier looks like
a slug, otherwise a case-insensitive substring match against registered repo names, with ambiguity
surfaced rather than guessed.

## Why This Matters

Typing a full `owner/name` slug every time is needless friction when an operator usually has only
one repo in mind and can identify it by a fragment of its name. But guessing wrong is worse than
asking: silently picking one of several matching repos could install a team into the wrong
checkout, so this story is exactly as much guessing as is safe, and no more — a single unambiguous
match resolves silently, anything else stops and asks the operator to be specific.

## Architecture Notes

- Two resolution paths, chosen by the shape of the identifier itself, never by trying both and
  merging results:
  1. **Contains `/`** → exact `owner/name` match only. Resurrects `GetRepoBySlug` (previously
     present in the registry, per the research brief) rather than reimplementing slug lookup.
  2. **No `/`** → case-insensitive substring match against `Name` across every repo returned by
     `ListRepos()`.
- Zero matches is a not-found error naming exactly what was searched for (the raw identifier as
  typed). Exactly one match resolves silently. More than one match is an `AmbiguousRepoError`
  listing every matching repo's full `owner/name`, refusing to guess — mirrors the existing
  `AmbiguousIssueError` presentation pattern elsewhere in the codebase rather than inventing a new
  error shape.
- This story's output is a single resolved repo (path + slug); it has no opinion on what happens
  next — US-9's write engine (T-20) is the only consumer, calling this resolver once per `team add`
  invocation before doing anything else.
- No changes to the repo registry's storage format — this story only adds a resolution function on
  top of `ListRepos()`/`GetRepoBySlug`, both already-existing primitives.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | An identifier containing `/` is resolved only by exact `owner/name` match; substring matching is never attempted for it. |
| AC-2 | An identifier with no `/` that uniquely matches one registered repo by case-insensitive substring resolves to that repo without prompting. |
| AC-3 | An identifier matching more than one registered repo fails, listing every match's full `owner/name`, rather than resolving to any one of them. |
| AC-4 | An identifier matching no registered repo fails, naming the identifier that was searched for. |

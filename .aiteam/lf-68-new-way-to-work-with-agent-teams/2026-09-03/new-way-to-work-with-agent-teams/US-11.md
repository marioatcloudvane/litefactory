# US-11 — `team update` (single-worktree)

> As a platform operator, I want to bring a repo's installed agent files back in line with the
> current team definition, without losing any file I've hand-edited, so that picking up upstream
> improvements doesn't mean re-installing from scratch or manually diffing every file.

Delivers `team update`, scoped explicitly to the one worktree the command is run against. Updating
every worktree that happens to share a repo is out of this story's scope entirely — that is US-15's
job, sequenced after this one.

## Why This Matters

Once a team's upstream definition moves on, the installed copy in a repo goes stale unless
something brings it forward. Doing that safely means using US-10's classification to only touch
files that can be updated without risk, and refusing — loudly — to touch the ones that can't. This
story deliberately does only that much: it does not try to reach into every other checkout of the
same repository a developer might have on disk, because that turned out to be a materially harder
problem (there's no existing data link between a registered repo and its worktrees) and folding it
in here would have re-created the same kind of premature-complexity mistake the three-hash model
already was. That harder problem is its own story, built on top of this one once this one is solid.

## Architecture Notes

- **Scope, resolved explicitly (this is the rescoping this pass makes):** `team update` acts only
  on the worktree named by `--repo` (or the current directory), exactly as every other `team`
  command does. It does not discover or touch any other worktree of the same repository. The
  multi-worktree case — propagating the same update to every other checkout — is entirely US-15's
  scope; this story has no partial or best-effort behavior toward it and makes no attempt at it.
- Update behavior is driven by US-10's classification, per file:
  - **In sync** — nothing to do.
  - **Upstream updated** — safe to update; re-render and atomic-write via US-9's write engine.
  - **Missing** — re-render and write (equivalent to reinstalling that one file).
  - **Locally modified** / **Conflict** — refuse by default, report the file and its classification,
    and require an explicit `--force` (documented as destructive) to overwrite; even under
    `--force`, `team update` never silently discards a hand-edit without saying so in its output.
- `--migrate-config` (carried over from earlier planning) has no remaining referent under the pure
  index model — there is no legacy config layer to migrate into. **Resolved: the flag is dropped
  from this story entirely**, not deferred; if a real migration need appears later it is a new
  story, not a revival of this flag.
- Reuses US-9's atomic-write engine and lockfile update (a successful update rewrites the affected
  lockfile records' `sourceHash`/`renderedHash` to match what was just written) — this story adds no
  new write primitive of its own.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | `team update` updates every In-sync, Upstream-updated, and Missing file automatically, and leaves every Locally-modified or Conflict file untouched, reporting each by name and classification. |
| AC-2 | `--force` overwrites Locally-modified/Conflict files only when explicitly passed, and its output names exactly which files it overwrote. |
| AC-3 | Running `team update` against one worktree never modifies any other worktree checked out from the same repository. |

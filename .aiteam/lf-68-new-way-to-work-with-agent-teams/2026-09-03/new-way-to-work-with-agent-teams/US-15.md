# US-15 — Multi-worktree propagation for `team update`

> **PLACEHOLDER (2026-09-05).** This is a new story added by the 2026-09-05 narrow reconciliation
> pass, in response to the sponsor's third refinement ("`team update` must propagate to every
> worktree of a repo"). Full task breakdown, architecture notes, and acceptance criteria are
> **deferred to the follow-up planning pass** — this file exists only to hold the story's place in
> `plan_brief.md`'s Story Index and to record its scope and dependency now, before that detail is
> written.

> As a platform operator working across multiple git worktrees of the same repository, I want
> `litefactory team update` to bring every worktree up to date, not just the one I ran it from, so
> that I don't end up with worktrees silently drifting out of sync with each other.

**Scope (one line):** extend `team update` (US-11) so that a single invocation, run from any
worktree, propagates its changes to every other worktree of the same repository — rather than
updating only the working tree it was invoked in.

**Depends on:** US-11 (`team update`, single-worktree). This story must ship after US-11, not in
parallel with it.

**Known open questions for the follow-up pass** (not resolved here): how worktrees of the same
repo are enumerated (`git worktree list` vs. a litefactory-maintained registry); what happens when
a sibling worktree is missing, locked, or itself has uncommitted, conflicting local edits at the
same owned paths; whether propagation is atomic across all worktrees together or per-worktree.

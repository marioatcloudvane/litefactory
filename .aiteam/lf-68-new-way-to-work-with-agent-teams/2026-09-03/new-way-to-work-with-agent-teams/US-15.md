# US-15 — Multi-worktree propagation for `team update`

> As a platform operator who checks the same repository out in more than one place, I want
> `team update` to bring every one of my worktrees up to date together when I ask it to, so that I
> don't have to remember to re-run the command separately in each checkout.

Delivers an opt-in `--all-worktrees` mode for `team update` that discovers every other worktree of
the same repository and applies US-11's single-worktree update algorithm to each, independently.

## Why This Matters

Developers routinely keep more than one working copy of the same repository checked out at once —
one per branch, one for a long review, one for a quick fix. US-11 deliberately updates only the
worktree it's run against, because litefactory's data model has no existing link between a
registered repo and the worktrees checked out from it, and inventing one felt exactly like the kind
of premature schema commitment that produced the three-hash model this whole feature is walking
back from. This story solves the same problem a lighter way: instead of persisting a relationship
that might turn out wrong, it asks git itself, every time, which worktrees actually exist right now,
and only ever touches the ones git confirms.

## Architecture Notes

- **No new persisted schema relationship.** Resolved per the research brief's recommendation:
  worktree discovery is computed live at update time by running `git worktree list` against the
  repository, using its output as the sole ground truth for which paths are real, current worktrees
  of this repo. Any other signal that might hint at a sibling worktree (recorded session history, a
  collision-set from repo registration) is treated only as a candidate to check, never as a fact —
  it is filtered through `git worktree list`'s live output before anything is touched, and a
  candidate git does not confirm is silently excluded, not treated as an error.
- `--all-worktrees` is opt-in on `team update`; without it, `team update` behaves exactly as US-11
  specifies (current worktree only). This story adds no new default behavior to US-11 itself.
- Each confirmed sibling worktree has its own independent `.litefactory/` bookkeeping directory
  (lockfile, and any US-13 overrides) — propagation runs US-11's full per-worktree algorithm
  (classify via US-10, update the safe states, refuse Locally-modified/Conflict) separately against
  each worktree's own bookkeeping state. A hand-edit in one worktree does not block the update of a
  sibling worktree that has none.
- Failure in one worktree (e.g. a renderer error, a lock held by another process) is reported for
  that worktree and does not abort propagation to the others — the command's final report lists a
  per-worktree outcome, not one pass/fail for the whole operation.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | `team update --all-worktrees` updates the current worktree plus every other worktree `git worktree list` confirms belongs to the same repository, applying US-11's algorithm independently to each. |
| AC-2 | A candidate worktree path not confirmed by `git worktree list` is never touched and never reported as an error — it is simply excluded. |
| AC-3 | Without `--all-worktrees`, `team update` touches only the worktree it was run against, exactly as US-11 specifies. |
| AC-4 | A failure updating one worktree is reported against that worktree specifically and does not prevent the others from being updated. |

# US-14 — Allowlist + forbidden-flag + secret-scan validation

> As a security-conscious platform operator, I want every parameter `team manage` can set to be
> checked against a closed allowlist, a value validator, and litefactory's existing secret
> scanner, so that `team manage` can never be used to smuggle in a dangerous flag or a credential.

This story exports the one piece of validation infrastructure US-13's `team manage` command needs
to enforce that guarantee, and owns the acceptance criteria for the guarantee itself.

## Why This Matters

`team manage` is deliberately the easiest way to change an agent's configuration, which is exactly
why it needs the strictest guardrails: without them, it would be the path of least resistance for
a dangerous flag or an accidentally-pasted credential to end up committed into a repo's config.
This story makes sure that door stays shut — the allowlist must stay closed permanently, not
loosen over time into "any key," and the two existing scanners already trusted elsewhere in
litefactory (forbidden-flag detection, secret detection) are reused here rather than
re-implemented, so there is exactly one place either check can be wrong.

## Architecture Notes

- This is a minor, intentional deviation from the original spec (recorded as DEV-2 in
  `plan_brief.md`): `config.forbiddenFlag()` is refactored into an exported
  `config.ContainsForbiddenFlag`, so SEC-1's single-grep-site guarantee has exactly one
  construction/check point. No new import edge is introduced by this refactor.
- The allowlist itself, its range validation, and its enforcement point are implemented as part of
  US-13's T-31, which is this story's sole consumer. This story owns the acceptance criteria on
  the resulting validation behaviour and the one exported predicate T-31 depends on — not a
  second copy of the enforcement logic.
- The allowlist must remain closed: "any key is settable" is never an acceptable relaxation of it.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-1 | `team manage set` on a parameter not on the allowlist is a usage error listing the allowlist; nothing is written. |
| AC-2 | `team manage set temperature=9` (out of the valid range) is rejected by range validation. |
| AC-3 | `team manage set` on a value that would construct a forbidden flag is rejected before anything is written. |
| AC-4 | `team manage set` on a value that trips the secret scanner is rejected before anything is written, and the matched text never appears in the error message. |

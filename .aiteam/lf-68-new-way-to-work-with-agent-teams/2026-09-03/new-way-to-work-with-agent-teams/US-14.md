# US-14 — Validation: forbidden-flag and secret-classification checks on team-authored content

> As a platform operator, I want litefactory to refuse to write an agent definition that smuggles in
> a dangerous CLI flag or an unredacted secret, whether that content came from the shipped index or
> from a per-repo override, so that installing a team can't be turned into a way to slip something
> harmful into a repo.

Delivers validation shared across every write path this feature has — `team add`, `team update`,
and US-13's override mechanism — reusing `internal/config`'s existing secret-classification and
forbidden-flag logic rather than inventing a parallel check.

## Why This Matters

Every other story in this feature can end with litefactory writing a file into someone else's repo.
That's exactly the kind of operation that needs a check in place before the write, not after: a
markdown source (whether shipped, statically overridden, or a per-repo US-13 override) is not fully
trusted just because it came from a resolved index entry, since an override in particular is
operator-supplied at write time. This story is what stands between "the index says to write this"
and the write actually happening.

## Architecture Notes

- Reuses `config.ClassifySecret` and the newly-exported `config.ContainsForbiddenFlag` (DEV-2,
  `plan_brief.md` Deviations) rather than duplicating either check inside `internal/team`. This is
  the reason `internal/team`'s import restriction (US-1) names exactly these two.
- **Dependency, updated this pass:** validation runs against whatever mechanism actually produces
  the content being written — which, after US-13 resolved Open Question 6, includes an override's
  local markdown file, not only an index-resolved source. Every write path (US-9's `team add`/
  US-11's `team update`, and any override recorded by US-13) runs the same two checks before the
  atomic write, with no path exempted because it's "just a local override."
- Validation runs on the **rendered output bytes** per harness (post-US-5), not on the raw markdown
  source — a forbidden flag or secret pattern could in principle be introduced by a renderer's own
  templating, not only by the source content, so checking post-render is the only point that covers
  both.
- A validation failure aborts the whole write (consistent with US-9's all-or-nothing guarantee) and
  names the offending agent key, harness, and which check failed — never a partial write with the
  bad file skipped.

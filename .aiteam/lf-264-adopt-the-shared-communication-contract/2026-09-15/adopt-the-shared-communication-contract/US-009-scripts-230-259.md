# One-off upgrade scripts for #230 and #259

Run 0017 follows the owner's selected pending scope: **#230 and #259 only**.
The two entrypoints never enumerate or act on other parents. Other open records
are deliberately outside this script run; that does not delete or change them.
Assumption: these numbers identify parent tasks in `marioatcloudvane/litefactory`.
The factory verifies that each is an eligible managed legacy scope.

## Run previews

From the repository root, set the script directory and an evidence directory:

```sh
script_dir='.aiteam/lf-264-adopt-the-shared-communication-contract/2026-09-15/adopt-the-shared-communication-contract'
evidence_dir="$PWD/upgrade-evidence-230-259"
"$script_dir/upgrade-230.sh" --output-dir "$evidence_dir"
"$script_dir/upgrade-259.sh" --output-dir "$evidence_dir"
```

Requires Python 3 and the existing configured factory. The default executable is
`/Users/mariomh/litefactory/dist/litefactory`; override with `--executable` plus
an absolute path. The wrapper does not build, replace or restart it. Normal
`LF_HOME` configuration selects the factory; no credentials are passed to the
script. Use the same configuration for preview and apply.

Default execution invokes only the supported `story-contract upgrade <parent>
--preview`. This is an **operator-side authenticated forge read** through the
factory, not an offline inventory. It leaves database schema, story content and
readiness unchanged. Each invocation prints a newly created private evidence
directory containing `preview.json` with task, executable hash, LF_HOME,
timestamps, stdout, stderr and exit status. Review that file. Failed previews
retain their diagnostics and never lead to apply. Output directories inside
LF_HOME are refused.

## Apply each reviewed preview

Use the actual successful `preview.json` paths printed above:

```sh
"$script_dir/upgrade-230.sh" --output-dir "$evidence_dir" \
  --apply --reviewed-preview "$evidence_dir/upgrade-230-REPLACE/preview.json"
"$script_dir/upgrade-259.sh" --output-dir "$evidence_dir" \
  --apply --reviewed-preview "$evidence_dir/upgrade-259-REPLACE/preview.json"
```

`--apply` is an explicit operator mutation. It invokes the existing factory
upgrade, which can migrate its database schema, retain upgrade intent and publish
the selected parent's unfinished cohort. The wrapper first checks the selected
task, binary hash and LF_HOME against the reviewed preview, obtains another
read-only preview, and refuses if the output changed. The factory's own apply
rechecks source revisions and eligibility; the wrapper is not an atomic lock
against changes between calls. Do not change factory configuration while running
these commands.

Each wrapper is independent: a failure for #230 does not prevent previewing #259.
No batch command silently applies both. An explicit `--apply` without a reviewed
preview is rejected before the factory runs. A new executable requires a new
preview. The 300-second per-command timeout can be adjusted with `--timeout`.

## Refusals and interrupted publication

- If the factory requires a planning scope, use the supported owner `/plan ...`
  or `replan` flow on that parent and wait for its run to exit, then preview again.
  These scripts do not automatically send comments or invalidate readiness.
- Active attempts, pending legacy deliveries, ambiguous conversion and changed
  revisions remain factory refusals. Let normal completion/recovery settle them
  or resolve the reported conflict through Plan, then repeat the preview.
- If apply fails, times out or is interrupted, retain the whole evidence directory.
  A `running` or `uncertain` apply record is not success. Do not assume no writes
  happened. Obtain a new preview, review its retained partial-publication state,
  then use the same task wrapper with explicit apply and that new preview. The
  factory resumes its retained intent; the wrapper never retries automatically.
- A successful apply still needs the next published Plan and an explicit
  `/implement ...` request to approve/freeze it before engineering resumes.

CLI observations are supporting evidence, not fabricated receipts or acceptance.
The factory retains authoritative upgrade intent. Completed stories, historical
acceptance and workflow versions are preserved by the existing upgrade flow.
Saved Markdown files are not migrated. These scripts do not prove global drain,
close US-009, or authorize removing any legacy reader.

Implementation is confined to these two shell entrypoints and the shared
`upgrade_pending.py` driver. No live preview or migration was executed during
script development; verification uses a fake factory executable only.

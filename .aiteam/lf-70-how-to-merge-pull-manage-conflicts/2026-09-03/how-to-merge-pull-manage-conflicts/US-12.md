# US-12 — Apply a confirmed resolution and complete the merge

> As the issue owner, after reading a suggested resolution, I want to confirm
> it in a comment and have litefactory apply it and finish the merge, so that I
> do not have to reproduce the fix by hand — and I want nothing applied unless
> I said so.

Two separate turns linked by a stored row. The blocked run ends after posting
a suggestion. A later, explicit confirmation comment from the owner — naming
the proposal ID and carrying the confirmation phrase — starts a second, agent-
free turn that applies only the listed files, completes the merge, and
discloses everything it did.

## Why This Matters

This is the story that turns a suggestion someone can only read into a branch
that is actually fixed, and it is the only story in this entire feature that
lets model-produced text become committed bytes. That is exactly why it is
worth having and exactly why it is the riskiest thing this plan proposes:
a feature that can be talked into writing something other than what a human
approved is a materially different risk than a feature that only ever
suggests. What is unresolved: nobody has yet read a real proposal in
production, so this story does not open until one has been observed, and the
confirmation gate is deliberately built so there is no configuration, label,
or environment setting that can ever bypass it — the only way anything gets
written is a human saying so, by name, after the fact.

## Architecture Notes

- **Pattern:** `internal/daemon/proposals.go` for the lifecycle half —
  expire-first, ownership check on session **and** commenter login, status
  guards on every transition, refusals as values. `internal/turn/command.go`'s
  `KindSchedule` for the grammar half: a litefactory-owned control command,
  parsed by its own grammar, that never starts an agent run.
- **Package placement:** grammar in `internal/turn/command.go` plus a sibling
  parser; dispatch and validation in `internal/daemon`; the application turn in
  `internal/turn`; the mutators in `internal/git` on `*Worktree`; replies in
  `internal/report`.
- **Key interfaces:** an unexported `confirmedProposal` value that only the
  confirmation validator constructs, and that the application function
  requires as a parameter. That is what makes the confirmation gate a compile-
  time property rather than a runtime `if` someone could later forget.
- **The genuinely net-new part:** confirmation arrives as a comment (daemon),
  but application needs a worktree under the CloneGate (turn). This story
  therefore introduces a third turn shape: an agentless apply turn. It reuses
  `prepareClone` unchanged (gate, fetch, `freezeSlug`, `ensureWorktree`) and
  the existing commit-and-push path, and skips the harness entirely — what is
  new is the run kind and three git mutators, not new git plumbing.
  **Rejected alternative:** letting the next ordinary run apply a `confirmed`
  proposal inside `syncBase` instead of starting a dedicated turn. Cheaper and
  needs no new turn shape, but the owner confirms and nothing visible happens
  until they happen to trigger another run, which contradicts the expectation
  that confirming produces the commit and a comment naming it. Recorded and
  rejected, not overlooked.
- **Concurrency/context:** the application runs inside the existing
  session/clone serialisation and never concurrently with another turn on the
  same worktree. The stored base and branch SHAs are re-verified **inside**
  the gate, immediately before writing. No new locking primitive, no second
  gate acquisition, no per-branch keyed gate.
- **Integration point:** `internal/git` gains exactly three `*Worktree`
  mutators — write the listed resolved paths (contained to those paths only),
  stage those paths, complete the in-progress merge — plus reuse of the
  dormant unmerged-path classification already in `internal/git/status.go`.
  Commit trailers extend the existing trailer mechanism in
  `internal/git/commit.go` with three new values: the proposal ID, the
  confirming human's handle, and the model name. Never a `Co-authored-by:`
  trailer for the model — that would attribute authorship to a non-account.
- **Watch out:** (1) the git method-set allowlist test lands **before** the
  first mutator exists, not after — `*Worktree` has no such test today and the
  moment it can write model-influenced content its method set becomes a
  security boundary; (2) never add a general-purpose `Reset`, `Checkout`, or
  `Apply` to `*Worktree`, and never add `Reset` as a self-heal after a failed
  rollback; (3) path containment for resolved files must be enforced by
  `*git.Worktree` itself — rejecting absolute paths, `..` traversal, symlink
  components, and anything not in the proposal's file list — never by the
  caller and never by string-prefix comparison; (4) a non-owner confirmation
  must not move the proposal's status off `pending`; (5) "yes" or a reaction is
  not consent — the confirmation phrase and the proposal ID are both required;
  (6) the commit identity prelude (`-c user.name= -c user.email= -c
  commit.gpgsign=false`) is mandatory, not defensive — the daemon's child
  process environment carries no identity or signing configuration and
  omitting the gpgsign flag risks a hang; (7) if some files were excluded from
  the original proposal, applying it resolves only the listed ones and the
  merge is not completed while conflicts remain.
- **Depends on:** US-11 (there is nothing to confirm without a stored
  proposal), US-10 (the rollback guarantee covers the failed-application
  path), and the same Phase 7.5 security review gating US-11. Opens only after
  US-11 has shipped and at least one real blocked run has produced a
  suggestion the owner has actually read — an observation gate, not a
  calendar date, because this story's whole risk is a function of suggestion
  quality and nobody has seen one yet.
- **NOT in scope:** any bypass of the confirmation gate, in any form — no
  config value, label, flag, environment variable, or trusted-repo exemption;
  applying an owner's hand-edited version of a suggestion rather than the
  stored one; retrying a failed application inside the same run; touching the
  base branch; force-push; history rewrite.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-12.1 | A test asserts that no code path writes to the worktree, the index, or a commit for a proposal whose status is not `confirmed`; the gate has no bypass. |
| AC-12.2 | A confirmation from a non-owning author is refused, writes nothing, leaves the status at `pending`, and is reported in the thread. |
| AC-12.3 | A confirmation naming an unknown, expired, superseded or already-decided proposal writes nothing and is reported with the reason. |
| AC-12.4 | A valid confirmation whose stored base/branch SHAs no longer match the current tips marks the proposal `superseded`, writes nothing, and asks for a fresh suggestion. |
| AC-12.5 | A valid confirmation on an unchanged branch writes only the files named in the proposal, produces exactly one merge commit carrying the run trailers plus the proposal and confirmer trailers, and the comment names the model, the confirmer, the files and the commit. |
| AC-12.6 | A forced failure part-way through application leaves the branch at its pre-application SHA with no in-progress merge state and no modified tracked files. |
| AC-12.7 | An attempt to write a path outside the proposal's file list — absolute, traversing, symlinked, or simply unlisted — is refused by `internal/git`, aborts the application, and leaves the branch unchanged. |
| AC-12.8 | `TestWorktreeMethodSetIsTheAllowlist` exists and passes; each mutator added to `Worktree` appears in it with a recorded reason. |
| AC-12.9 | Confirming the same proposal twice produces no second commit and is reported as already applied. |
| AC-12.10 | No run is held open waiting for a confirmation; propose and apply are two independently terminal runs. |

# US-11 — Suggest a resolution when a run is refused for a conflict

> As the issue owner, when litefactory refuses my run because the base branch
> conflicts with my task branch, I want it to suggest how the conflict could be
> resolved, so that I can judge the fix without reconstructing the conflict
> myself.

Produced only for a run whose sync outcome is `blocked`. Reads the conflicting
hunks, asks a narrow tool-free model call for a resolution, validates the
answer locally, stores it as a pending proposal, and posts it. Writes nothing
to the branch, the index, or a commit.

## Why This Matters

Today a blocked run ends with a list of file names and no way forward except
opening an editor by hand. That is a dead end, and it is the single biggest
gap this whole feature leaves open: knowing you are blocked is not the same as
knowing how to get unblocked. This story turns the dead end into a decision —
a candidate fix the owner can read and judge — without letting litefactory
touch the branch on its own initiative. What is still unresolved and
deliberately left that way: nobody on this project has yet read a real
suggestion, so whether these proposals are actually good enough to be useful
is an open question this story does not answer. It also opens a new kind of
cost and exposure — repository file content now leaves litefactory for a model
on litefactory's own initiative, for the first time — which is why this story
ships behind a dedicated security review and defaults to off until that review
signs off.

## Architecture Notes

- **Pattern:** `internal/agent/proposal.go` end to end — bounded request
  struct, prompt builder placing untrusted text last under an explicit "data,
  not instructions" label and delivering it on stdin, strict parser with
  `DisallowUnknownFields` and trailing-value rejection, semantic validation
  left to the caller. Then `internal/daemon/proposals.go` for the lifecycle:
  expire-first, validate-locally, failure-as-a-value.
- **Package placement:** the model-call types in `internal/agent`; the
  narrowing interface, hunk collection, capping and orchestration in
  `internal/turn`; the row in `internal/store`; the rendering in
  `internal/report`. Nothing new in `internal/daemon` for this story.
- **Key interfaces:** a one-method `ConflictAdvisor` declared by `internal/turn`
  and satisfied by type-asserting a `Runner` out of `turn.RunnerSet` by
  `agent.Kind` — `internal/daemon/proposal_adapter.go:19-29` is the shape. A nil
  advisor means "no suggestion", not "error".
- **Concurrency/context:** collect and cap hunks **inside** `prepareClone`'s
  gate; make the model call **outside** it. Carry the turn's `context.Context`
  into the call; never `context.Background()`. Give the call its own deadline,
  distinct from the git budgets (`Divergence` 30s, `MergePreview` 60s,
  `MergeBase` 60s) — it is a different kind of wait.
- **Integration point:** `syncBase` (the last step of `prepareClone`, after
  `ensureWorktree`) produces the block and `MergePreview.Conflicts`. A new
  `report.ReplyKind` needs a matching case in `replyKind` at
  `internal/turn/report.go:722`; `internal/report` cannot import `internal/turn`,
  so this is always both edits, never one.
- **Watch out:** (1) do not extend `harness.PromptInput` with a content field —
  that would put file content into every ordinary run's prompt; (2) exclude
  over-budget, binary, and non-UTF-8 files whole, never truncate them —
  truncation mid-file produces a payload that corresponds to no real file; (3)
  reject a bad response in full — never salvage the good files out of it, the
  same reject-don't-salvage discipline `internal/report` already applies to
  untrusted text; (4) a failed, disabled, timed-out, or unusable-response model
  call must leave the existing conflict refusal byte-identical plus exactly
  one added line, never degrade it; (5) migration number is `0008`, and MUST
  be re-confirmed by listing `internal/store/migrations/` at implement time,
  not read out of this document — the number was wrong once already this week.
- **Depends on:** US-4 (the `blocked` outcome), US-5 (path rendering
  discipline), US-8 (config), US-9 (`0007` landing first so `0008` is next).
  Ships in the phase opened after a blocking security review (Phase 7.5, scope:
  repository content outbound to a model, model text inbound) signs off, and
  `suggest_conflict_resolution` defaults to **false** until that sign-off,
  flippable by the architect or that review per the spec's own escape clause.
- **NOT in scope:** any write to the branch, index or a commit; the
  confirmation grammar that lets a human accept a proposal (that is US-12); the
  ability to edit a suggestion before applying it; any second model call; a
  "reasoning" tier — this resolves to the default model tier and adds no new
  `config.Tier` value.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-11.1 | A blocked run with suggestions enabled posts one comment carrying the conflicting files, a per-file suggested resolution, the model name, a proposal ID and the confirmation phrase; the branch SHA is unchanged after the run. |
| AC-11.2 | With the advisor stubbed to fail or time out, the run still produces the full existing conflict refusal, writes no proposal row, and adds exactly one line saying no suggestion could be produced. |
| AC-11.3 | With `suggest_conflict_resolution: false`, the blocked run is byte-identical in behaviour and comment content to the no-suggestion path and makes no model call. |
| AC-11.4 | A response naming a path outside `MergePreview.Conflicts`, and separately one containing conflict markers, each produce no proposal; both cases are covered by tests. |
| AC-11.5 | Conflicting content in the prompt is capped per file and in total per `conflict_content_max_bytes`; over-budget, binary and non-UTF-8 files are excluded whole and named in `Excluded`; a test asserts the cap and the treatment. |
| AC-11.6 | The blocked run reaches a terminal state after posting; no code path sleeps, polls or waits for a reply. |
| AC-11.7 | A test asserts the model call is not made while the CloneGate is held. |
| AC-11.8 | A new proposal for a session supersedes any earlier pending one in a single transaction; a session never has two pending proposals. |
| AC-11.9 | No test or production path writes conflicting file content to the store. |

# US-10 — Guarantee the branch is untouched when sync fails

> As the owner of a task, I want an absolute guarantee that if syncing my
> branch goes wrong, my branch ends up exactly as it was before litefactory
> tried, so that an automatic feature I don't watch closely can never be the
> reason my work is damaged.

This story is the rollback guarantee behind every other story in this plan:
proof that a failed, timed-out, or aborted merge attempt leaves the task
branch byte-identical to how it stood before the attempt began.

## Why This Matters

Every other story in this plan asks the owner to trust an automatic process
with their branch — trust that a clean merge really was clean, trust that a
refusal really did stop before doing damage, trust that a skip really
changed nothing. That trust has exactly one foundation: a failure of any
kind, for any reason, must never leave the branch in a worse or different
state than before litefactory touched it. This story is where that promise
stops being an assumption behind the other nine stories and becomes something
that is actually tested against timeouts, aborts, and mid-merge failures, not
just against the tidy conflict case.

## Architecture Notes

- Enforcement mechanism: capture the branch's HEAD SHA before attempting
  `MergeBase`, and on any non-`synced` outcome — `blocked`, `failed`, or a
  timeout — run `merge --abort` and then re-verify the captured SHA against
  the actual HEAD. The guarantee is proven by that re-verification, not
  assumed from `merge --abort` alone.
- Explicitly forbidden mechanism (S-5): never use `git reset` as the
  self-heal path for a failed merge — `Reset` is off-limits on `*git.Worktree`
  for reasons unrelated to this feature (see `plan_brief.md` Cross-Story
  Constraints, Security) and this story does not get an exception. Abort-then-
  verify is the only accepted pattern.
- Timeout handling: a merge that times out must be distinguishable from one
  that fails outright — `MergeBase`'s error path needs a way to signal
  `TimedOut` specifically, not collapse it into a generic failure, because the
  recovery step (abort, verify SHA) is identical either way but the
  *disclosure* (US-3's `failed` outcome) should be able to say which one
  happened.
- This story's test is the empirical proof of the rollback guarantee end to
  end: inject a mid-merge failure (or simulate a timeout) and assert the
  branch SHA before and after are identical, not merely that no error
  propagated further than it should have.
- Depends on US-2 (`MergeBase` must exist before its failure paths can be
  tested).
- NOT in scope: retrying a failed sync automatically (no retry mechanism
  exists or is proposed anywhere in this plan); the conflict-list rendering
  that accompanies a `blocked` outcome (US-4/US-5); persisting the outcome
  (US-9) — this story proves the branch state guarantee, not the disclosure
  around it.

## Acceptance Criteria

| ID | Criterion |
|----|-----------|
| AC-10.1 | After a merge attempt that ends in `blocked`, `failed`, or a timeout, the task branch's HEAD SHA is byte-identical to its HEAD SHA immediately before the attempt began, verified by explicit comparison rather than inferred from the absence of an error. |
| AC-10.2 | A timed-out merge attempt is reported through a distinguishable `TimedOut` path, not collapsed into the same generic failure as an unrelated git error. |

### The core gap: cost is captured, tokens are not

- `internal/agent/result.go:76-168` defines `agent.RunResult`, the struct litefactory builds from a coding-agent subprocess's output. It carries `Outcome`, `Model string`, `Tools []string`, `ResultText`, `CostUSD float64`, `HasCost bool`, `NumTurns int`, and timestamps. **It has no token fields of any kind** — no input/output tokens, no cache tokens, no per-model breakdown.
- `HasCost` exists specifically to distinguish "reported zero cost" from Codex's stream, which the code comment says "reports token usage but no monetary amount" (`internal/agent/result.go:120-122`) — i.e. the codebase already anticipated a coding agent that reports tokens without cost, but nothing consumes that signal today.
- `internal/harness/meta.go:41-124` — `harness.Meta`, the schema written to each run's `NNNN.meta.json` artefact (spec ID S-3). It mirrors `RunResult` plus turn-supplied fields (SessionID, Branch, SHAs). `CostUSD *float64` is nullable (lines 110-112). **No token fields here either.**
- **The database schema has no token or model columns.** `internal/store/migrations/0001_init.sql:84-105` (extended by `0003_agent.sql:47`) defines the `runs` table as: `id, session_id, segment_id, ordinal, mode, agent, trigger_comment_id, status, exit_code, error, started_at, finished_at, duration_ms, cost_usd REAL, log_path, commit_sha, result_comment_id`. Confirmed exhaustively via the `runColumns` list in `internal/store/runs.go:606-609`. **Only `cost_usd` persists. There is no `num_turns`, no `model`, and no token columns anywhere in the schema.**
- `store.RunOutcome` / `store.FinishRun` (`internal/store/runs.go:236-253`) — the only cost-shaped field written back after a run finishes is `CostUSD *float64`. `duration_ms` is computed by the store itself from `started_at`/`finished_at`, never trusted from the caller — an existing precedent for "derive, don't trust the subprocess" that a metering feature should probably follow for tokens/cost too, or explicitly decide not to.

### Claude's and Codex's raw event streams: both already flow through litefactory, and both are mostly discarded (this pass)

This pass read `internal/harness/runner.go`, `internal/harness/stream.go`, and `internal/codex/runner.go` in full to settle, directly, exactly what litefactory sees on the wire today and what happens to it. This also **resolves Open Question 1 from the second pass** ("does Claude's fuller data already flow through and get silently dropped, mirroring the confirmed Codex situation?") — the answer is **yes, definitively, for both agents**.

**Claude**, invoked with `-p --output-format stream-json --verbose` plus session/tool/model/settings flags (`internal/harness/runner.go:425-460`, both the `Run` and `Classify` paths). `stream-json` is the *richer* of Claude Code's two output formats — not the single-final-result `json` format — so litefactory already receives Claude's full per-message event stream on stdout, not a summary. But `eventStream.consume`/`observe` (`internal/harness/stream.go:97-187`) only fully decodes two event shapes:
  - `type: "system", subtype: "init"` → five fields (`Model`, `Tools`, `SessionID`, `CWD`, `PermissionMode`).
  - `type: "result"` → five fields (`IsError`, `Result`, `TotalCostUSD`, `DurationMS`, `NumTurns`).

  **Neither struct has a field for `usage` or `modelUsage`.** The second pass's web research (Domain / Problem Space §1 below) already established, independently and from Anthropic's own docs, that the real `result`-type message *does* carry `usage` and `modelUsage`. Put the two together: **Claude's per-model, per-token-type breakdown is already arriving on litefactory's stdin today, on every run, and is silently dropped because `resultEvent` (`stream.go:65-71`) has no field to catch it in.** This is not a "new wire-format work needed" situation — it is a "add two fields to an existing struct and read them" situation, for the token/cost side of the feature specifically. Every other event type (`assistant`, `tool_use`, `tool_result` — including any carrying `parent_tool_use_id` for sub-agent nesting) is counted (`s.events++`) and otherwise dropped without inspection.

  Critically, `eventStream.write` (`stream.go:125-138`) appends **every raw line, unconditionally, verbatim** to the run's log file *before* `observe` ever tries to decode it — so even the event types litefactory's own code never looks at are not lost; they are persisted (see below).

- **Codex**, invoked with `exec --json` (`internal/codex/runner.go:242-272`), Codex's own streaming event-per-line mode — the analogous "richer" format. `consume` (`runner.go:281-333`) also writes every raw line to the log file unconditionally, then decodes into an inline struct with only `Type`, `ThreadID`, `Message`, `Item.Type`, `Item.Text` — **no `usage` field**, confirming precisely what the first pass established by grep (`runner.go` has zero occurrences of "usage"/"token" in its decode logic) but now confirmed by full read: the `usage` object proven present on `turn.completed` (`internal/codex/runner_test.go:22`) is parsed off the wire into the raw log line and then dropped, identically to Claude's pattern. Also confirmed this pass: `agent.RunResult.NumTurns` is **never set** by `internal/codex/runner.go` — it stays zero for every Codex run today, a pre-existing, metering-adjacent gap on the same "one struct, two populate sites" surface.

### The raw stream is already persisted to disk, unabridged, for every run (this pass)

`log_path` in the `runs` table (`internal/store/runs.go:210,218`) resolves via `naming.RunLogPath(home, ref, ordinal)` to `<RunsDir>/NNNN.jsonl` (`internal/naming/paths.go:97-101`) for **both** agents. Both runners open this file directly (`O_CREATE|O_WRONLY|O_APPEND`, mode 0600) and use it as the literal sink for the raw event stream — `internal/harness/stream.go:125-138` for Claude, `internal/codex/runner.go:291` for Codex. **`log_path` is the raw subprocess stdout, byte-for-byte, one JSON line per event, for both agents — not a derived or post-processed artefact.** There is no separate summary-only log; `NNNN.meta.json` (from `harness.Meta`) is a distinct, separately-written parsed-summary file.

**This is the single most important fact for the owner's reconstruction question.** For every run litefactory has ever executed and retained the log directory for, the full raw event stream — every `assistant`/`tool_use`/`tool_result` event, with whatever nesting/attribution fields Claude's or Codex's wire format actually carries — is already sitting on disk in `NNNN.jsonl`, unparsed past two event types. Reconstructing sub-agent-level (or richer per-model) usage after the fact does **not** require changing how litefactory invokes either agent, and does not require new capture code running during a live run — it requires **new parsing code that re-reads files litefactory already writes today**, retroactively, for any run whose `NNNN.jsonl` still exists on disk. (Caveats on how far this actually gets you — especially for sub-agent-level attribution specifically — are in Domain / Problem Space §4 below; the wire data existing is necessary but not sufficient for full per-sub-agent cost attribution.)

### Coding-agent abstraction: `agent.Runner`, and what a third coding agent would need (this pass)

The interface both existing agents implement is deliberately minimal: `agent.Runner` (`internal/agent/kind.go:37-39`) has exactly one method, `Run(ctx context.Context, req Request) (*RunResult, error)`. `internal/harness.Runner` (Claude) and `internal/codex.Runner` (Codex) both satisfy it structurally. Registration is via `turn.RunnerSet` (`internal/turn/execute.go:42`), `type RunnerSet map[agent.Kind]Runner`, built once at daemon startup (`internal/daemon/runners.go:30-51`) and keyed by `agent.Kind` — a **string-keyed map, not a hardcoded enum** (`internal/agent/kind.go:5-14`'s doc comment states `agent.Kind` "carries no vocabulary of its own"). Only two implementations exist today (`internal/harness`, `internal/codex`); no third `agent.Runner` implementation was found in the tree.

**What this means for metering specifically:** the *interface* needs no change to add a third coding agent (that extensibility already exists, by design). But the *data each agent's wire format actually offers* is not uniform (see Domain / Problem Space §5 for the Codex-specific detail) — different field names, different granularity (Claude has `cache_creation`/`cache_read`; Codex has `cached_input_tokens`/`cache_write_input_tokens`/`reasoning_output_tokens`, a different but comparably granular vocabulary), and very different protocol-stability guarantees (Claude's is a documented, versioned SDK contract; Codex's is explicitly, officially undocumented-as-stable — see §5). A metering feature that wants to stay agent-agnostic as more coding agents are added needs **one shared internal token/cost schema** (e.g. a normalized `(run_id, model, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, cost_usd)` row shape) fed by **one small per-agent adapter each** — a `usage`-extraction function living alongside each agent's existing populate-site (`internal/harness/runner.go:620-654` for Claude, `internal/codex/runner.go:216-221` for Codex) — rather than one generic parser that assumes a common wire shape. This mirrors the existing `RunnerSet` pattern (one small implementation per agent behind a shared interface) rather than introducing a new one.

### One run = one top-level subprocess; sub-agent cost is invisible to litefactory today

- One `runs` row corresponds to one top-level coding-agent subprocess invocation, triggered once per triggering GitHub comment, resolved in `daemon.run` (`internal/daemon/tick.go:1380`).
- Nested Task-tool sub-agent calls (e.g. a research-orchestrator invoking `codebase-tour` and `web-researcher`, as happened in all three passes of this very run) execute **inside** that one subprocess and are entirely invisible to litefactory's data model today — they roll up into the single parent run's `cost_usd` and whatever final result event Claude reports.
- Practical consequence: **cost/tokens per mode are already naturally separable** (one `runs.mode` per run, already populated). **Cost/tokens per sub-agent within a mode are not observable at all** with current instrumentation, though — as established above — the raw data needed to *attempt* reconstruction is already being written to disk and simply not parsed. ### 4. Reconstructing sub-agent-level Claude usage from logs after the fact — how far it actually gets you

**One important distinction up front, established by cross-referencing this pass's codebase and web findings.** There are two different "Claude logs" in play, and they should not be conflated:
- Anthropic's own internal session transcript, written by the Claude Code CLI itself to `~/.claude/projects/<project>/<session-id>.jsonl` on the machine running Claude Code. Anthropic's docs explicitly describe this file as **internal to Claude Code, subject to change between versions, and discourage parsing it directly** — the docs point instead to `/export`, `-p --output-format json|stream-json`, `--resume`, the hook `transcript_path`, or the Agent SDK's live message stream as the supported ways to get structured data.
- **litefactory's own `NNNN.jsonl`** (Codebase Context, above) — which is simply litefactory's own captured copy of the documented `stream-json` wire output it already requested via `--output-format stream-json`. This is not the same file Anthropic's caution is about; it is litefactory's own recording of a documented, supported output format. The caution above does not directly apply to it, though the *contents* of that documented format still carry the caveats below.

Given that distinction, here is what the documented `stream-json` format (and hence litefactory's `NNNN.jsonl`) can and cannot support for sub-agent reconstruction:

- **The richer per-message data (`parent_tool_use_id`) exists only in `stream-json` output, never in the single-shot `json` format** — confirmed directly from Anthropic's docs. Since litefactory already invokes with `--output-format stream-json` (Codebase Context, above), this data is already reachable in principle without any change to how litefactory invokes Claude.
- **But by default, `stream-json` only forwards `tool_use`/`tool_result` blocks for sub-agents, not their text or per-message usage.** Full subagent message/usage visibility requires an additional flag, `--forward-subagent-text` (or the `CLAUDE_CODE_FORWARD_SUBAGENT_TEXT` env var), available since CLI v2.1.211+; nested sub-agent depth (a sub-agent's own sub-agent) is only visible in the stream from v2.1.219+. **litefactory's observed invocation flags (Codebase Context, above) do not include `--forward-subagent-text`.** This is a concrete, actionable gap: as things stand today, even a from-scratch parser reading litefactory's existing `NNNN.jsonl` files would not see full sub-agent usage data for historical runs — that flag would need to be added going forward for future runs to carry it. This is a genuinely new finding, not previously flagged in either prior pass.
- **Anthropic does not publish a worked reconstruction method, and its own documented example code explicitly skips subagent messages** when computing per-step usage (`!message.parent_tool_use_id`), relying only on the final `result` message for the true count. There is **no documented way to identify the "last" message of an individual sub-agent's own sub-conversation** — the only available signal is that the sub-agent's `Task`-tool `tool_result` appears once in the parent stream when the sub-agent finishes, which is an inference from stream shape, not a documented API contract. Whether each per-step message even carries an explicit `model` field (needed to attribute tokens to a model per sub-agent, not just per top-level run) was **not confirmed** against an official source this pass.
- **The same output-token-placeholder caveat already on record applies at sub-agent granularity too**: only the true end-of-turn message carries a real `output_tokens` figure; intermediate per-step figures are placeholders. So a naive sum over all per-step events for a given `parent_tool_use_id` would double-count or undercount unless the parser specifically identifies each sub-agent's true final message — which, per the point above, has no documented marker.
- **Cost reconstruction per sub-agent is mechanically plausible but not an Anthropic-endorsed technique.** `total_cost_usd`/`modelUsage[...].costUSD` are official running totals for the whole call, by model only. Applying a price table (the SDK's bundled table, or the `modelPricing` override already on record from the second pass) to token counts regrouped by `parent_tool_use_id` would be a caller-constructed inference, not a documented workflow — and it recovers a dollar figure only for the "already reported cost, redistributed by sub-agent's share of tokens" approach, not a fully independent per-sub-agent cost.
- **Not researched this pass, flagged as an open question**: whether any community or Anthropic-provided tooling already does this stream-json-to-sub-agent-usage reconstruction, which would materially change the "build vs. reuse" calculus. `web-researcher` did not reach this question within this pass's scope.

**Direct answer to the owner's question ("is this possible?"):** partially, and with real, non-cosmetic gaps, not a clean yes. The raw wire data (`parent_tool_use_id`, per-message `usage`) is real, documented, and — per the Codebase Context findings above — already being captured verbatim to disk by litefactory today (modulo the missing `--forward-subagent-text` flag, which would need adding for *future* runs to carry full sub-agent detail). But there is no documented method for identifying a sub-agent's true final (non-placeholder) usage message, no documented per-sub-agent cost field at all, and reconstructing cost specifically requires building a price-table-based estimate on top of token counts rather than reading a reported figure. This is a real, buildable feature, but it is an estimation/heuristic layer litefactory would design and own, not a field Anthropic exposes and litefactory would simply read — meaningfully different in kind from the per-model breakdown (§1-3, prior pass), which is a documented field litefactory is simply not reading yet.

**Source.** [code.claude.com/docs/en/sessions](https://code.claude.com/docs/en/sessions), [code.claude.com/docs/en/headless](https://code.claude.com/docs/en/headless) (subagent-forwarding flag and version gates), [code.claude.com/docs/en/agent-sdk/cost-tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking) (documented example code skipping subagent messages, placeholder-output-tokens caveat). Confidence: high for the documented mechanics (flag names, version gates, format restriction to stream-json); medium for the composite "reconstruct sub-agent cost" technique, which is explicitly an inference built from documented primitives rather than a documented workflow itself.

### 5. Codex — the same questions, answered for OpenAI's coding agent

"Codex" here is the **Codex CLI** (`openai/codex` on GitHub, a Rust implementation), run non-interactively via `codex exec --json` — this matches exactly the invocation litefactory already uses (Codebase Context, above) and the `usage` object shape already proven on the wire by `internal/codex/runner_test.go:22`.

**What Codex reports, and how granular it is.** No dollar cost is reported anywhere in Codex's event stream — confirmed on OpenAI's own non-interactive-mode docs, consistent with what the codebase already signals via `agent.RunResult.HasCost`'s doc comment. Token usage is **not** flat input/output the way the first pass's grep-only finding might have suggested — it is comparably granular to Claude's cache breakdown, just under different field names: `input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens` (confirmed via an official docs example), plus `cache_write_input_tokens` and a `total_tokens`/`blended_total()` helper found in Codex's own protocol source (`codex-rs/protocol/src/protocol.rs`). So a metering feature does not need to treat Codex as a lesser, flatter data source than Claude for token granularity — it needs to treat it as differently-shaped but similarly rich, with the cost figure specifically absent and requiring litefactory's own price table (already the recommended design from the second pass, for exactly this reason).

**Per-model breakdown.** Not present. Codex's `TokenUsage` struct carries no `model` field, and no `modelUsage`-analogous per-model breakdown was found in the protocol source or docs — usage is aggregated at session/turn level only. Separately (community-sourced, **not officially confirmed** — flagged accordingly), Codex CLI reportedly supports switching models mid-session via a `/model` command since some CLI version; if true, this would mean a single Codex session could span more than one model with no way, today, to attribute tokens back to which model produced them. This is architecturally different from Claude, where `modelUsage` already solves this even for sub-agents.

**Sub-agents.** Codex CLI does have an officially documented subagents feature (`/agent` to inspect/switch agent threads, delegation via `AGENTS.md`/skills), and its own docs warn that "subagent workflows consume more tokens than comparable single-agent runs" — but **usage/cost is aggregated at session level only**, with **no documented per-subagent breakdown field and no public equivalent of `parent_tool_use_id`**. Codex's internal protocol source does carry `parent_turn_id`/`root_turn_id` fields on an internal `Submission` struct, suggestive of some causal threading structure existing internally, but these are **not documented or exposed on the public `usage`/`turn.completed` events** — a materially weaker starting point for sub-agent-level reconstruction than Claude's documented `parent_tool_use_id`, not a parallel opportunity.

**Pricing.** OpenAI's official current pricing (fetched this pass, superseding earlier aggregator-only figures from the second pass's scope) lists only `gpt-5.3-codex` in the Codex family: $1.75/1M input, $0.175/1M cached input (~90% cache discount, structurally similar to Anthropic's cache-read discount pattern), $14.00/1M output; a "fast mode" tier doubles all three. Two things reinforce the second pass's "must be versioned, not hardcoded" conclusion, independently, on the Codex side: model SKUs appear to churn faster than on the Claude side (`gpt-5-codex`/`gpt-5.2-codex`, seen in earlier aggregator data, appear superseded by `gpt-5.3-codex` on the current official page), and OpenAI's own pricing/docs URLs recently migrated (`platform.openai.com` → `developers.openai.com`/`learn.chatgpt.com`), independent evidence that this vendor's documentation and product surface is actively being restructured, not a settled reference to build a static table against.

**Protocol stability — the most consequential difference from Claude.** Codex's own maintaining repository states directly: "the de facto wire protocol is defined in `protocol.rs`, though it is not 'stable' today." OpenAI ships tooling to generate a pinned schema snapshot matched to the exact installed Codex version (`codex app-server generate-ts`, `codex app-server generate-json-schema`), explicitly **with no cross-version stability guarantee**. This is a categorically different posture from Claude's documented `SDKResultMessage`/`ResultMessage` contract (second pass, §1) — a metering feature's Codex adapter should be built defensively (tolerant of unknown/renamed fields, versioned against the installed Codex CLI version, probably schema-checked or re-verified on Codex CLI upgrades), where the Claude adapter can lean more on a stable documented contract.

**Direct answer to the owner's second question:** Codex is not a lesser version of the Claude story, it is a *differently-shaped and less stable* one. Token granularity is comparable (cache/reasoning breakdown exists, just different field names); cost is never reported and must be computed by litefactory from a price table (already anticipated in the second pass's Codex-specific recommendation); per-model breakdown does not exist even in principle today; sub-agent attribution has a weaker (undocumented, internal-only) foundation than Claude's `parent_tool_use_id`; and the wire protocol itself is explicitly, officially not guaranteed stable across versions, which the Claude side does not share. A metering design that stays agent-agnostic as more coding agents are added needs a shared internal schema (Codebase Context, above) fed by adapters that are allowed to differ significantly in confidence and defensiveness per agent — not a single parser assumed to generalize.

**Source.** [learn.chatgpt.com/docs/non-interactive-mode](https://learn.chatgpt.com/docs/non-interactive-mode) (canonical redirect target of `developers.openai.com/codex/noninteractive`), [learn.chatgpt.com/docs/agent-configuration/subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [developers.openai.com/api/docs/pricing](https://developers.openai.com/api/docs/pricing), [github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs), [github.com/openai/codex/blob/main/codex-rs/app-server/README.md](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md). Confidence: high for all directly-quoted doc/source statements (event field names, the "not stable today" statement, pricing figures, subagent-usage-aggregation-only statement); low-medium specifically for the `/model` mid-session-switch claim, which rests on community blogs only with no official OpenAI page found to confirm it.

## Constraints & Risks

- **`[V]` Schema change is unavoidable, as the issue owner anticipated**, and now more precisely scoped than the first pass could establish. The `runs` table has no columns for tokens, per-model breakdown, or even `num_turns` (already computed in memory but never persisted for Claude, and not even computed for Codex — see below). Since Claude's own result data confirms a genuine, populated `modelUsage`/`model_usage` per-model map exists on the wire (and litefactory's own parser is confirmed, this pass, to already receive but drop it), a normalized child table (one row per `run_id` + `model`, carrying input/output/cache-read/cache-write tokens and cost) is the schema shape indicated by the data itself — not a hypothetical "might a run use more than one model" concern, but a documented, always-present field.
- **`[V]` (this pass) Claude's per-model token/cost data does not require new wire-format work — it requires reading two fields litefactory's own parser already discards.** `internal/harness/stream.go`'s `resultEvent` struct decodes `IsError`/`Result`/`TotalCostUSD`/`DurationMS`/`NumTurns` from the `result` event but has no field for `usage` or `modelUsage`, both of which are confirmed present on that same event by Anthropic's own docs. This is the single cheapest, most concrete slice of the whole feature: add two fields to an existing struct in an already-read code path.
- **`[V]` Sub-agent-instance-level cost attribution is confirmed not available from any documented, supported field**, and (this pass) reconstructing it after the fact from litefactory's own already-captured logs is possible in outline but has real, non-cosmetic gaps: no documented marker for a sub-agent's "true final" (non-placeholder) usage message, no documented per-sub-agent cost field at any granularity, and litefactory does not currently pass the `--forward-subagent-text` flag needed to even receive full sub-agent message/usage detail in the stream (so historical `NNNN.jsonl` files, and current-invocation ones until that flag is added, are missing this specifically, even though the top-level per-model breakdown is unaffected). **"Tokens/cost per mode" (already supported today via `runs.mode`) and "tokens/cost per model within a run" (§ above — cheap, data already on the wire) should be treated as the practical near-term scope**; "cost per sub-agent instance" is confirmed, now with more precision, to be a separate, larger, estimation-based initiative — not a field to read, but a heuristic layer to design, build, and caveat — that Plan mode should explicitly scope out or defer.
- **`[V]` Reported cost figures are estimates, not billing-authoritative.** Anthropic's own docs state `total_cost_usd`/`costUSD` are computed client-side from a bundled price table and must not be used for billing decisions. A metering feature built on this data should describe itself accordingly (e.g. "estimated cost," not "cost") to avoid setting a false expectation of billing-grade accuracy.
- **`[V]` Per-step token counts are unreliable; only the final result message (or per-model map) is trustworthy**, and even that can be zeroed out on some error subtypes. Any parsing logic litefactory adds must read the final `result` message, not accumulate per-step `assistant` message usage, and must treat an error-subtype run's zeroed usage as "unknown," not "zero cost." This same placeholder caveat applies, unresolved, at sub-agent granularity too (see above).
- **`[V]` Two coding agents exist in production (Claude, Codex) with asymmetric data availability, asymmetric pricing stories, and (this pass) asymmetric protocol stability guarantees.** Codex already emits token usage on the wire (confirmed, comparably granular to Claude's cache breakdown, just under different field names) but litefactory discards it and never attaches a dollar figure, meaning Codex needs the versioned/overridable pricing table discussed below where Claude's own reported cost should simply be persisted as-is. New this pass: Codex's own maintaining repository states its wire protocol is explicitly "not stable today," with no cross-version schema guarantee — a materially weaker foundation than Claude's documented SDK contract, meaning a Codex parsing adapter should be built more defensively (tolerant of missing/renamed fields, checked against the installed Codex version) than the Claude one.
- **`[V]` A price table, if litefactory builds one for the Codex/recompute path, must be versioned and overridable, not a one-time hardcoded constant** — mirroring Anthropic's own documented approach (a bundled table plus a `modelPricing` override) rather than reinventing a different pattern. It does not need to be live-fetched; no such API is documented to exist. This pass adds independent evidence for the same conclusion on the OpenAI side: Codex model SKUs (`gpt-5-codex` → `gpt-5.2-codex` → `gpt-5.3-codex`) appear to have already churned, and OpenAI's own pricing/docs URLs were mid-migration at the time of this research — a static, hardcoded Codex price table would need at least as frequent review as the Claude one, plausibly more.
- **`[V]` (this pass) A metering design that stays agent-agnostic as more coding agents are added should be a shared internal schema plus one adapter per agent, not one generic parser.** The `agent.Runner` interface (`internal/agent/kind.go:37-39`) and the string-keyed `turn.RunnerSet` (`internal/turn/execute.go:42`) already anticipate a third coding agent at the interface level, but the two agents' wire formats differ in field names, granularity, and — critically — protocol stability guarantees. A single shared parser assuming a common shape across agents would either miss Codex's differently-named cache/reasoning fields or be brittle against Codex's unstable protocol; per-agent adapters feeding one shared internal token/cost row shape avoids both.
- **`[V]` Two stale doc-comments in `internal/store/runs.go` (lines 40-42 and 51-56) understate what the codebase already does** (multi-mode dispatch, live Codex dispatch). Low risk in itself, but a reason Plan mode should verify current behavior against live dispatch code (`daemon/tick.go`, `daemon/runners.go`) rather than trusting nearby comments.
- **`[O]` The owner explicitly wants us to question the verb `meter`.** No alternative was evaluated this run beyond noting the request — this is a naming/UX decision better suited to Plan mode's requirements conversation with the owner than something Research mode should pre-decide. Candidate alternatives worth raising in Plan mode: `cost`, `usage`, `spend`, `bill(ing)` — `meter` itself is defensible (utility-metering connotation fits "measuring consumption after the fact") but is unconventional as a CLI verb compared to more common `cost`/`usage` naming in adjacent tools; this is a judgment call for the requirements conversation, not a fact this run can settle.
- **`[V]` Redaction boundary applies only if metering output ever becomes forge-facing.** CLI output (local) is currently exempt from redaction by design; if a future iteration posts periodic cost summaries as GitHub comments, that would cross into `report`/`turn`'s redacted path and needs to be an explicit design decision, not an oversight.
- **`[R0]` A prior spike on this exact topic exists** (`.aiteam/lf-parallelization/2026-09-01/token-improvements/SPIKE.md`, a different session, not read this run) and should be treated as required reading for Plan mode before finalizing scope, to avoid re-deriving or contradicting prior thinking.
- **`[W]` A single, unconfirmed community bug report** (GitHub issue #112 on `claude-agent-sdk-typescript`) claims `usage.output_tokens` and `modelUsage[model].outputTokens` can disagree even in a single-model session with no subagents — with no maintainer response as of this research. Not blocking, but worth a note in any implementation: prefer `modelUsage` as the source of truth for persisted per-model figures over the top-level `usage` object, both because it is documented to be the more complete field (includes subagents) and because of this unresolved discrepancy report.
- **`[W]` (this pass) A prompt-injection artifact appeared inside one `web-researcher` search result during this pass** (a fabricated `CLAUDE.md`/`MEMORY.md` dump and a spurious "background agent" notice, per the sub-agent's own report). It was not acted on and had no bearing on any finding above, but is recorded here as a genuine anomaly worth the owner's and Plan mode's awareness — a reminder that any future implementation consuming untrusted web/tool content (if a metering feature ever ingests external pricing pages automatically, for instance) should treat that content as data, not instructions, the same discipline `web-researcher` itself demonstrated here.

## Recommended scope for Plan mode

Plan mode should cover:
- A schema design for token/model capture: a `runs`-scoped extension (nullable columns, following the existing `CostUSD *float64` convention for "unknown" vs. "zero") plus a normalized child table keyed on `(run_id, model)` carrying input/output/cache-read/cache-write tokens and per-model cost — the child table is now justified by a confirmed, always-present `modelUsage`/`model_usage` field in Claude's own output, not a hypothetical, and this pass confirms the concrete, cheap first step: two new fields on `internal/harness/stream.go`'s `resultEvent` struct.
- Wiring Claude's per-model, per-token-type data (`usage`, `modelUsage`, `total_cost_usd`, `num_turns`) into `agent.RunResult` → `harness.Meta` → the `runs`/child-table schema, preferring the already-reported `total_cost_usd`/`modelUsage[...].costUSD` over any independently recomputed figure wherever Claude supplies it — reserving recomputation-from-raw-tokens-and-a-price-table for the Codex case specifically, where cost is not currently attached to the reported token usage.
- Wiring Codex's own token fields (`input_tokens`, `cached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `cache_write_input_tokens`) into the same shared schema via a Codex-specific adapter, built more defensively than the Claude adapter given Codex's own maintainers describe its wire protocol as explicitly not stable across versions — and fixing the pre-existing gap where `agent.RunResult.NumTurns` is never set for Codex runs, since it sits on the same populate-site surface this feature already needs to touch.
- A design for the shared internal token/cost schema explicitly built to be **agent-agnostic at the schema level, with one small adapter per coding agent** (mirroring the existing `agent.Runner`/`turn.RunnerSet` extensibility pattern) rather than a single generic parser — informed by this pass's finding that Claude and Codex differ meaningfully in field names, granularity, per-model support, and protocol stability, and that more coding agents are expected to be added later.
- A scoping decision, made explicitly rather than assumed, on **whether sub-agent-instance-level attribution is in scope at all for this feature's first iteration.** This pass shows it is more feasible than previously known — the raw data litefactory needs is already, or could easily be, captured to disk (`NNNN.jsonl`) — but it is not a simple "read a field" addition: it requires (a) adding `--forward-subagent-text` to litefactory's Claude invocation, (b) new parsing logic re-reading already-captured logs, (c) an unresolved methodological gap around identifying a sub-agent's true final usage message, and (d) for cost specifically, a caller-built estimation layer rather than a documented field — and it has a weaker starting point on the Codex side (no public `parent_tool_use_id` equivalent) than on Claude's. Recommend treating this as an explicit "phase 2 / defer" candidate distinct from the "tokens per mode" and "tokens per model within a run" scope, which are both comparatively cheap and already well-supported by documented, existing fields.
- If a price table is built (needed for the Codex path, and for any sub-agent-cost estimation on the Claude side), design it as versioned and overridable per model ID, not per model family — mirroring Anthropic's own `modelPricing`-override pattern — and budget for Codex model SKUs churning at least as fast as Claude's, based on this pass's observation that `gpt-5-codex`/`gpt-5.2-codex` already appear superseded by `gpt-5.3-codex`.
- A new `internal/cli/cmd_meter.go` command following the `cmd_logs.go` pattern exactly (DB-first with meta.json fallback, `--repo`/task-ref parsing via the existing helpers, daemon-stopped/no-IPC precedent), with `[repository]`/`[task-id]` positional scoping and `--mode`/`--ca` filters, both of which are supportable today against existing populated columns without a schema change.
- A decision, made in the Plan-mode requirements conversation with the owner, on the CLI verb (`meter` vs. alternatives) and on how deep sub-agent-level attribution should go given the cost/complexity tradeoff established above.
- Reading and reconciling with the prior spike at `.aiteam/lf-parallelization/2026-09-01/token-improvements/SPIKE.md` before finalizing scope.

Plan mode should **not** need a further web-research pass for the Claude Code/Agent SDK wire-format questions, the Codex/OpenAI cost-and-token questions, or the sub-agent-reconstruction mechanics — all are now resolved to the depth this research effort could reach (see Domain / Problem Space §1-5).

### 1. What Claude Code CLI / the Claude Agent SDK actually reports per run

The final `result`-type message (`SDKResultMessage` in the TypeScript SDK, `ResultMessage` in Python; identical shape reachable from `-p --output-format json`/`stream-json` on the plain CLI) carries:

- `total_cost_usd` — a cumulative cost estimate for the whole `query()`/CLI invocation.
- `usage` — the standard Messages-API shape: `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`.
- `modelUsage` (TypeScript, camelCase) / `model_usage` (Python, snake_case) — **a map keyed by model name**, each entry carrying per-model `inputTokens`/`outputTokens`/`cacheReadInputTokens`/`cacheCreationInputTokens`/`costUSD`, plus (CLI v2.1.246+) a `costBasis` field (`list`/`managed`/`unknown`) recording which price table priced that model's most recent request.
- `num_turns`, `duration_ms`, `duration_api_ms`, `session_id`, `is_error`, `uuid`, `subtype` (`success`/`error_during_execution`/`error_max_turns`/`error_max_budget_usd`/`error_max_structured_output_retries`), and `permission_denials`.

So the answer to the issue's own framing ("is it just a total cost figure?") is **no — a full breakdown by token type and by model is already present in the data Claude Code returns**, not something litefactory would need to derive or request specially. The CLI and both SDK bindings expose "the same usage data with different field names/casing" (Python's `usage` is a plain dict rather than a typed object).

Two documented caveats material to schema design:
- `total_cost_usd`/`costUSD`/`modelUsage[...].costUSD` are **explicitly documented as client-side estimates**, computed locally from a bundled price table, **not authoritative billing data** — Anthropic's own docs say not to use them for billing end users; the authoritative source is the separate Usage and Cost API / Console. A metering feature built on this data is therefore an *estimate-tracking* tool, not a billing-reconciliation tool, and should probably say so in its own output.
- Per-step `output_tokens` on intermediate `assistant` stream messages is a **documented placeholder** (reflects only `message_start`, not the true end-of-turn count) — a metering implementation must read the final `result` message's `usage`/`modelUsage`, never sum per-step assistant-message token counts, or it will undercount output tokens.
- On some error results (`subtype: "error_during_execution"` after a crash), `usage`/`total_cost_usd`/`modelUsage` **may all be zeroed** despite real consumption having occurred; Anthropic's docs describe a fallback of using the prior turn's result or summing per-step `assistant` message usage in that case — worth carrying into a metering design as an explicit "unknown cost" state rather than silently recording `$0`.

**Source.** [Track cost and usage — Agent SDK](https://code.claude.com/docs/en/agent-sdk/cost-tracking), [TypeScript SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript), [Run Claude Code programmatically (headless)](https://code.claude.com/docs/en/headless), [CLI reference](https://code.claude.com/docs/en/cli-reference). Confidence: high — read directly from Anthropic's current primary docs, including field-level code samples.

One unresolved wrinkle worth flagging rather than smoothing over: a filed, unanswered GitHub issue ([claude-agent-sdk-typescript#112](https://github.com/anthropics/claude-agent-sdk-typescript/issues/112)) reports a single-model session where top-level `usage.output_tokens` did not match `modelUsage[model].outputTokens`, while `total_cost_usd` matched the `modelUsage`-derived figure — suggesting `modelUsage` may be the more reliable field to treat as ground truth, though the discrepancy isn't fully explained by documented behavior for a single-model case (see next section for the documented, *expected* usage/modelUsage divergence for multi-agent cases). Medium confidence — one unconfirmed user report, no maintainer response as of this research.

### 2. Whether sub-agent/sub-step usage can be broken out — direct answer to the issue's framing

Anthropic's own docs contain a table explicitly titled around "the three result-level fields differ in what they count when the agent spawns subagents":

| Field | Includes subagent activity? |
|---|---|
| `usage` (top-level, on the result message) | **No** — main/top-level agent loop only |
| `total_cost_usd` | **Yes** — subagent requests are folded in |
| `modelUsage`/`model_usage` | **Yes** — subagent requests are folded in, broken down **by model**, not by individual subagent or by Task-tool call |

So: **a whole run is never reported as a single undifferentiated lump sum** — cost and tokens are already broken out by model within one run via `modelUsage`. But **no field in the documented schema attributes cost/tokens to an individual sub-agent instance or Task-tool invocation** — if two sub-agents in one orchestrator run use the same model, their contributions are indistinguishable inside `modelUsage`.

There is one documented escape hatch, at the raw-stream level rather than the result-summary level: in `--output-format stream-json`, every `assistant`/`user` message carries a `parent_tool_use_id` field — the ID of the `Agent`/Task-tool call that spawned it, `null` for the main session, and correctly set at nested depths (CLI v2.1.219+). Each of those per-message events carries its own `usage` object (subject to the same output-token-placeholder caveat above). A caller *could* reconstruct approximate per-sub-agent token counts by grouping raw stream events on `parent_tool_use_id` and deduplicating by message ID — but this is a build-it-yourself aggregation over the raw event stream, not something the SDK/CLI computes or exposes as cost. No dollar figure is attached to any of this at sub-agent granularity in the documented schema; cost is only computed at the whole-run (or whole-turn, in streaming-input mode) level.

Regarding "incremental" reporting: `usage`/`total_cost_usd`/`modelUsage` only appear on `result`-type messages, not emitted live by default. Single-shot mode: one `result` at the very end. Streaming-input mode (multi-turn within one `query()` call): one `result` per turn, with `usage` scoped to that turn's main loop only (still excluding subagents) while `total_cost_usd`/`modelUsage` carry the running total for the whole call — so cost is "live" at *turn* granularity in that mode, never at sub-agent or tool-call granularity.

**Direct answer to the open question as posed:** individual sub-agents cannot be broken out for **cost** purposes through any documented, supported field — only through raw stream-event reconstruction that litefactory would have to build itself, and even then only for token counts, not cost. A run is not a single lump sum overall (per-model breakdown is real and free), but it is effectively a lump sum **per sub-agent** unless litefactory chooses to parse and aggregate the raw stream by `parent_tool_use_id` — a materially bigger and lower-confidence undertaking than reading the final result message.

**Source.** [Track cost and usage — Agent SDK](https://code.claude.com/docs/en/agent-sdk/cost-tracking), [Run Claude Code programmatically (headless) — Follow subagent messages](https://code.claude.com/docs/en/headless). Confidence: high for the documented `usage`/`total_cost_usd`/`modelUsage` split and `parent_tool_use_id` mechanism — both stated explicitly and precisely in Anthropic's current docs.

### 3. Whether token prices (especially cache token types) are stable enough to hardcode

Cache pricing is structured as **fixed multipliers of each model's base input price**, largely uniform across the current model lineup, with one documented exception:

- 5-minute cache write: 1.25× base input price (uniform across current models).
- 1-hour cache write: 2× base input price (uniform across current models).
- Cache read (hit): 0.1× base input price for nearly every current model — **except** two specific models, which get a 0.025× multiplier instead.

These stack with other modifiers that also vary: a 50% Batch API discount, and a documented 1.1× data-residency multiplier (`inference_geo: "us"`) applied to *all* token categories for newer models.

But the base per-model input/output rates that these multipliers apply to **do change**, and the table itself is neither small nor static:
- Rates differ per model family and are not derivable from any formula.
- Anthropic's pricing page documents a concrete recent example of a scheduled price change (an announced increase) being reversed at the last stage rather than taking effect — i.e., real near-term repricing decisions happen and are not predictable from a hardcoded snapshot.
- Retired models keep their old (now off-lineage) prices on platforms that still serve them (Bedrock, Google Cloud) — a table needs to be versioned per model ID, not per model family, or it will misprice retired-but-still-invoked models.
- Pricing also varies by platform (direct API vs. Bedrock vs. Google Cloud vs. Claude Platform's CCU-based billing on AWS/Azure) — a single global table is not sufficient if litefactory ever needs to support more than the direct API.

Most tellingly: **Anthropic's own Agent SDK does not treat its bundled price table as permanently authoritative.** Its docs state the table is "bundled at build time," explicitly warn it can drift from actual billing "when pricing changes" or when "the installed SDK version does not recognize a model," and provide a `modelPricing` settings override specifically so operators can supply a current table rather than rely solely on whatever shipped with that SDK version.

**Direct answer to the open question as posed:** prices change often enough, and vary by enough dimensions (model, platform, and now data-residency), that a metering feature should **not** treat a hardcoded table as permanently correct — but it does not need a live-fetched/queried price API either (none is documented to exist). The pattern Anthropic itself uses — a bundled table with an explicit override/refresh mechanism, versioned per model ID — is the right model for litefactory to copy: ship a table, but make it overridable/updatable without a code change, and expect to revise it when new models ship or Anthropic revises pricing (as already happened once this year per the documented example above). In practice, though, litefactory should prefer to **persist whatever cost figure Claude's own result message reports** (`total_cost_usd`/`modelUsage[...].costUSD`) rather than recompute cost from raw token counts wherever that figure is available — recomputation is only needed for the Codex case, where tokens are reported without an attached dollar amount (confirmed in Codebase Context above), and that is exactly the situation where a versioned, overridable table becomes necessary rather than optional.

**Source.** [Anthropic Pricing — Model pricing / Prompt caching / Data residency pricing](https://platform.claude.com/docs/en/about-claude/pricing), [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [Track cost and usage — Agent SDK](https://code.claude.com/docs/en/agent-sdk/cost-tracking) (for the `modelPricing`/build-time-table caveat). Confidence: high for the multiplier structure and for "prices change and Anthropic's own SDK is explicitly designed for table drift" (both read directly from Anthropic's primary docs). Medium for the *historical cadence* of past price changes specifically — the pricing page shows current state plus one forward-looking example, not a changelog of all past revisions; exact frequency over the last 12-24 months was not established and is flagged as not settled below.

## Constraints & Risks

- **`[V]` Schema change is unavoidable, as the issue owner anticipated**, and now more precisely scoped than the first pass could establish. The `runs` table has no columns for tokens, per-model breakdown, or even `num_turns` (already computed in memory but never persisted). Since Claude's own result data confirms a genuine, populated `modelUsage`/`model_usage` per-model map exists on the wire, a normalized child table (one row per `run_id` + `model`, carrying input/output/cache-read/cache-write tokens and cost) is the schema shape indicated by the data itself — not a hypothetical "might a run use more than one model" concern, but a documented, always-present field.
- **`[V]` Sub-agent-instance-level cost attribution is confirmed not available from any documented, supported field.** `usage` excludes subagents entirely; `total_cost_usd`/`modelUsage` include them but only aggregated by model, never by individual sub-agent or Task-tool call. The only path to sub-agent-level granularity is parsing the raw `stream-json` event stream and grouping by `parent_tool_use_id` — a materially larger build than reading the final result message, and one that yields token counts only, with no attached dollar cost at that granularity. **"Tokens/cost per mode" (already supported today via `runs.mode`) should be treated as the practical ceiling for near-term scope**; "cost per sub-agent" is a distinct, much larger, lower-value initiative that Plan mode should explicitly scope out or defer rather than fold into this feature by default.
- **`[V]` Reported cost figures are estimates, not billing-authoritative.** Anthropic's own docs state `total_cost_usd`/`costUSD` are computed client-side from a bundled price table and must not be used for billing decisions. A metering feature built on this data should describe itself accordingly (e.g. "estimated cost," not "cost") to avoid setting a false expectation of billing-grade accuracy.
- **`[V]` Per-step token counts are unreliable; only the final result message (or per-model map) is trustworthy**, and even that can be zeroed out on some error subtypes. Any parsing logic litefactory adds must read the final `result` message, not accumulate per-step `assistant` message usage, and must treat an error-subtype run's zeroed usage as "unknown," not "zero cost."
- **`[V]` Two coding agents exist in production (Claude, Codex) with asymmetric data availability**, and now an asymmetric *pricing* story too. Codex already emits token usage on the wire but litefactory discards it, and (per the codebase findings) apparently without an attached dollar figure — meaning Codex is exactly the case that needs the versioned/overridable pricing table discussed above, while Claude's own reported cost should simply be persisted as-is and not recomputed.
- **`[V]` A price table, if litefactory builds one for the Codex/recompute path, must be versioned and overridable, not a one-time hardcoded constant** — mirroring Anthropic's own documented approach (a bundled table plus a `modelPricing` override) rather than reinventing a different pattern. It does not need to be live-fetched; no such API is documented to exist.
- **`[V]` Two stale doc-comments in `internal/store/runs.go` (lines 40-42 and 51-56) understate what the codebase already does** (multi-mode dispatch, live Codex dispatch). Low risk in itself, but a reason Plan mode should verify current behavior against live dispatch code (`daemon/tick.go`, `daemon/runners.go`) rather than trusting nearby comments.
- **`[O]` The owner explicitly wants us to question the verb `meter`.** No alternative was evaluated this run beyond noting the request — this is a naming/UX decision better suited to Plan mode's requirements conversation with the owner than something Research mode should pre-decide. Candidate alternatives worth raising in Plan mode: `cost`, `usage`, `spend`, `bill(ing)` — `meter` itself is defensible (utility-metering connotation fits "measuring consumption after the fact") but is unconventional as a CLI verb compared to more common `cost`/`usage` naming in adjacent tools; this is a judgment call for the requirements conversation, not a fact this run can settle.
- **`[V]` Redaction boundary applies only if metering output ever becomes forge-facing.** CLI output (local) is currently exempt from redaction by design; if a future iteration posts periodic cost summaries as GitHub comments, that would cross into `report`/`turn`'s redacted path and needs to be an explicit design decision, not an oversight.
- **`[R0]` A prior spike on this exact topic exists** (`.aiteam/lf-parallelization/2026-09-01/token-improvements/SPIKE.md`, a different session, not read this run) and should be treated as required reading for Plan mode before finalizing scope, to avoid re-deriving or contradicting prior thinking.
- **`[W]` A single, unconfirmed community bug report** (GitHub issue #112 on `claude-agent-sdk-typescript`) claims `usage.output_tokens` and `modelUsage[model].outputTokens` can disagree even in a single-model session with no subagents — with no maintainer response as of this research. Not blocking, but worth a note in any implementation: prefer `modelUsage` as the source of truth for persisted per-model figures over the top-level `usage` object, both because it is documented to be the more complete field (includes subagents) and because of this unresolved discrepancy report.

## Recommended scope for Plan mode

Plan mode should cover:
- A schema design for token/model capture: a `runs`-scoped extension (nullable columns, following the existing `CostUSD *float64` convention for "unknown" vs. "zero") plus a normalized child table keyed on `(run_id, model)` carrying input/output/cache-read/cache-write tokens and per-model cost — the child table is now justified by a confirmed, always-present `modelUsage`/`model_usage` field in Claude's own output, not a hypothetical.
- Wiring Claude's per-model, per-token-type data (`usage`, `modelUsage`, `total_cost_usd`, `num_turns`) into `agent.RunResult` → `harness.Meta` → the `runs`/child-table schema, preferring the already-reported `total_cost_usd`/`modelUsage[...].costUSD` over any independently recomputed figure wherever Claude supplies it — reserving recomputation-from-raw-tokens-and-a-price-table for the Codex case specifically, where cost is not currently attached to the reported token usage.
- A decision on whether to build raw-stream (`stream-json`, `parent_tool_use_id`) parsing for sub-agent-level token attribution, or explicitly scope that out as a separate, later initiative — this pass's research shows it is possible but categorically larger and lower-confidence than reading the final result message, and yields tokens only, never cost, at that granularity.
- If a price table is built for the Codex-recompute path, design it as versioned and overridable (per model ID, not per model family), mirroring Anthropic's own `modelPricing`-override pattern, rather than a single hardcoded constant map.
- A new `internal/cli/cmd_meter.go` command following the `cmd_logs.go` pattern exactly (DB-first with meta.json fallback, `--repo`/task-ref parsing via the existing helpers, daemon-stopped/no-IPC precedent), with `[repository]`/`[task-id]` positional scoping and `--mode`/`--ca` filters, both of which are supportable today against existing populated columns without a schema change.
- A decision, made in the Plan-mode requirements conversation with the owner, on the CLI verb (`meter` vs. alternatives) and on how deep sub-agent-level attribution should go given the cost/complexity tradeoff established above.
- Reading and reconciling with the prior spike at `.aiteam/lf-parallelization/2026-09-01/token-improvements/SPIKE.md` before finalizing scope.
- A short, targeted codebase-tour follow-up (Open Question 1 above) to confirm whether Claude's fuller result JSON is already flowing through `internal/harness/stream.go`/`runner.go` and being silently narrowed down, before assuming new parsing code is required from scratch.

Plan mode should **not** need a further web-research pass for the Claude Code/Agent SDK wire-format questions — those are now resolved (see Domain / Problem Space). It should still resolve the remaining open questions above (CLI verb, prior spike, litefactory's current Claude-side parsing depth, the unconfirmed SDK discrepancy report, price-change cadence, and multi-platform pricing) either through its own requirements conversation with the owner or a narrow, scoped codebase-tour follow-up — not by re-deriving them from memory.

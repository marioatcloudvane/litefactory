# Plan cross-check against issue #377

Review scope: the supplied authoritative revision-1 typed Plan (story-001 through story-003, AC-001–AC-032), the issue and owner-settled scope, RESEARCH_BRIEF.md and plan_brief.md. This is a requirements review, not implementation validation. No approved story, scope decision or plan brief was changed; no tests were executed.

## Verdict

The three-story plan covers the main design and preserves the owner's six decisions. It is a strong implementation outline, but it does not yet provide acceptance coverage for every promised behavior. In particular, completion of its current criteria would not establish lost-reply/restart recovery, the issue's Research-and-Plan terminal-result rule, or dependency-ordered drafting with the requested public ordinals. These are gaps to repair before treating the plan as complete coverage of #377, not new product decisions for the owner.

## Design ambiguities and precision improvements

- **Guard strength (AC-002, T-004/T-007).** Requiring a decoder and walking a registry is useful, but decoder presence alone does not prove that runtime execution cannot bypass the shared service. The negative guard should include a policy with a nominal decoder that tries to return a terminal-only result, and prove rejection. This strengthens the existing intent; it does not require implementing future workflows.
- **Preflight versus changing authority (AC-007 and plan_brief.md).** The statement that identical bytes which pass preflight must be accepted by submit is too absolute. Shared submission rechecks current authority/state. Specify identical validation at unchanged authority/state, while retaining rejection when revisions, authority or bindings become stale between calls. Preflight is not a reservation or approval.
- **Ask versus payload exclusivity (AC-004).** Define whether an ask response requires neither story branch or retains one. The approved shared-question mechanism must work without fabricating a complete story request or set. The contract examples should remove this ambiguity.
- **Temporary IDs (AC-005).** Names are explicitly unique; temporary IDs are not. Because dependency references and key mappings rely on temporary IDs, require unique, nonempty IDs and deterministic refusal of duplicates.
- **Waiting semantics (story-003 architecture constraints).** “Waiting stories do not block others” and “a story asking a question makes the loop wait” can coexist if the first concerns independent post-draft reviews and the second concerns a question during initial drafting. State that distinction; otherwise the two sentences appear inconsistent.
- **Decomposition quality (AC-023/AC-032).** A fake agent returning three entries proves orchestration, not that the real set role splits an independently deliverable scope well. Explicit decomposition guidance and the retained live tryout are the appropriate evidence; do not describe the fake-agent test as proving agent reasoning quality.

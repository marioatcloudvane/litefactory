# Research Brief — lf-119-claude-seems-to-take-a-lot-of-time-to

## Request

[O] When resuming a session, litefactory (via the Claude coding-agent runner) appears to take a very long time to come back — some runs take 20-30 minutes with no log update, and the delay is before the first API request comes through. Investigate whether this is tied to session-resumption mechanics (`--resume`) specifically, and if so, at what elapsed idle time ("staleness") the delay tends to appear.

## Codebase Context

### How litefactory invokes `claude` and decides resume vs. fresh

- [V] `internal/harness/runner.go:437-477` — the resume/fresh decision is expressed as a single flag choice: `sessionFlag := "--session-id"; if req.Path.Resuming() { sessionFlag = "--resume" }`, then `sessionFlag, req.Session.Ref` is appended to the `claude` argv. `--continue` is never constructed by litefactory (doc comment `runner.go:389-436`).
- [V] `req.Session.Ref` is a UUIDv5 derived purely in memory from `"<task ref>/segment/<ordinal>"` (`internal/naming/session.go:62-76`) — no filesystem or `~/.claude` I/O is involved in computing it.
- [V] The resume-vs-fresh decision itself (`internal/turn/prepare.go:426-476`, functions `previousRun` and `resumeDecision`) is driven entirely by litefactory's own SQLite run history (one `DB.ListRuns` query, then an in-memory loop over that session's own rows) — for the Claude runner, resume triggers iff a prior terminal run row exists for the same agent kind. **No code in this repository reads a Claude transcript file, scans `~/.claude/projects/*`, or does anything whose cost scales with the age or size of the Claude session being resumed.** This was verified by reading `runner.go`, `prepare.go`, `naming/session.go`, `harness/stream.go`, and `harness/settings.go` in full.

**Conclusion: the resume/fresh decision and argument construction inside litefactory's own Go code is O(1) and cannot itself account for a 20-30 minute delay.** If the delay correlates with resume, the mechanism is either (a) inside the `claude` binary itself, after litefactory hands off, or (b) in one of the two unlogged windows identified below, which happen to coincide with resume runs more often for incidental reasons (see Constraints & Risks).

### Where a silent gap could occur on litefactory's side

- [V] `internal/harness/runner.go:576,590-600` — `startedAt := time.Now()` is set immediately before `cmd.Start()`; the first log line ("coding agent started") is emitted only *after* `Start()` returns successfully. Everything before that point — request validation, `os.MkdirAll` for the log directory, `EnsureSettings` (`internal/harness/settings.go:162-176`, cheap: one `os.Stat`, writes only if the settings file is missing), opening the log file, and argv construction — produces no log line of its own. This window is normally sub-second but is, by construction, invisible in the log if something inside it were ever to stall.
- [V] `internal/turn/prepare.go:273-282` — `prepare()` emits its own single "run prepared" log line only at the very end, after `prepareClone` (git fetch, worktree setup), the DB reads, and attachment ingestion have all completed. A stall inside any of those steps is a second, larger silent-gap candidate that predates the `claude` invocation entirely and is unrelated to Claude's own resume mechanics:
  - [V] `internal/daemon/gate.go:86-100` (`cloneGate.Acquire`) — a channel-based lock with **no timeout by design** (documented trade-off, `gate.go:28-41`). If a sibling turn holds the same registered clone's lock, this blocks indefinitely and silently.
  - [V] `internal/turn/prepare.go:225` (`ingestAttachments`) — network fetch, gated behind `req.AttachmentsAllowed`. Its worst-case duration was **not verified** (file not opened in this tour) but is flagged as a second plausible silent-gap source.
  - [V] Individual git commands each carry fixed timeouts (`readTimeout=15s`, `fetchTimeout=60s`, `pushTimeout=120s`, `worktreeTimeout=120s`, `commitTimeout=120s`, `internal/git/exec.go:28-46`), single-attempt, no retry loop (`git/exec.go:138-188`) — these bound but do not eliminate a multi-minute wait if several git operations queue up.
- [V] No `time.Sleep`, polling loop, or backoff was found in any of the files read on the turn-execution path (`runner.go`, `prepare.go`, `execute.go`, `harvest.go`, `gate.go`, `git/exec.go`). **Not fully ruled out**: `internal/daemon`'s scheduler/tick loop beyond `gate.go` was not opened in this tour, so a scheduler-level wait outside a single turn's `Execute` call cannot be excluded from this evidence alone.

### A specific, higher-priority hypothesis surfaced by this tour

- [V] `internal/harness/settings.go:114` — litefactory's generated Claude settings **deny the `claude` process read access to `~/.claude/**`** for the runs it spawns. This is intended to sandbox the subprocess, but it means the `claude` binary is denied filesystem access to its own session store — the very directory (`~/.claude/projects/<hash>/*.jsonl`) that `--resume` needs to read to restore a session.
- This interaction was not something either sub-agent could test end-to-end (codebase-tour has no exec access to run `claude`; web-researcher has no access to this repository's settings file), so it is carried forward as the single most actionable open question in this brief: **does litefactory's own permission sandbox force `claude --resume` into a slow retry/fallback path (or a permission-denied error it silently swallows and retries) instead of failing fast?** If so, this would be a *litefactory-caused* regression, not an upstream Claude Code bug, and it would explain why the delay is tied to resume specifically rather than to session age per se.

## Domain / Problem Space

### What is documented and reported about `--resume` performance in Claude Code itself

- [W] Anthropic's own docs (`code.claude.com/docs/en/sessions`, fetched Sep 2026) state that `--resume` restores the full conversation from the local `.jsonl` transcript (all tool calls/results, model, agent, permission mode, active goals, scheduled tasks). Critically: **if a session has been inactive for more than roughly one hour *and* its transcript exceeds ~100,000 tokens (Pro/Max plans), the prompt cache has expired**, and the CLI shows a resume dialog; regardless of which option is chosen, the *first* subsequent message reprocesses the full history once. Choosing "Resume full session as-is" explicitly reprocesses and re-caches the entire history on that first message. This is the one **documented, primary-source** mechanism tying elapsed idle time to a real (though normally cache-related, not silent-hang) cost — and it requires *both* staleness *and* size, not staleness alone.
- [W] A cluster of GitHub issues on `anthropics/claude-code` describes `--resume` hanging or taking a very long time (multiple minutes to indefinite, requiring `kill -9`) specifically correlated with **large `.jsonl` transcript files** (6.8-16 MB single files, or aggregate history of hundreds of MB across a project) — not primarily with idle time:
  - `#52995` — hangs on large session files with very long individual lines; reporter explicitly states the issue is size-based, not age/staleness-based.
  - `#30302` — 12 MB transcript / 207 subagent files (107 MB aggregate); hypothesized eager-loading of all subagent `.jsonl` files during resume.
  - `#22204` — ~734 MB of aggregate session history across projects; diagnosis pointed at synchronous session-scanner loading during the resume picker's autocomplete.
  - `#21067` — large embedded tool-output data in the transcript (not paged to disk) causing indefinite hangs.
  - `#38029` — a large-session resume produced runaway token/usage consumption; the same-day release notes mentioned "improved memory usage and startup time when resuming large sessions," but the causal chain in the issue itself is speculative.
  - `#85800` — closest analogue to this report's symptom: a delay of roughly 10 minutes before the first response, recurring "after some idle/cold period," where the CLI's own internal duration accounting showed the tracked model API call was only ~12 seconds — i.e. the extra time was burned in **local session bootstrap before the API call**, not in the network request. This thread remains unresolved and speculative even among its own participants (one comment points at MCP server handshake fan-out rather than transcript size).
- [W] Workarounds reported in the community/issues: use `claude --continue` instead of `claude --resume <id>` (reported to take a different, faster code path that skips the picker's full-history scan); archive or delete oversized `.jsonl` transcripts under `~/.claude/projects/<project>/`; the `cleanupPeriodDays` setting to shorten the default 30-day retention window; choosing "Resume from summary" in the resume dialog instead of "Resume full session as-is" to avoid full-history reprocessing.
- [W] No evidence was found of a documented or reported "re-index the codebase" or project re-scan step that Claude Code runs on resume and that would scale with repository size. Absence-of-evidence caveat noted — this was a negative finding, not a confirmed non-existence.
- [W] macOS-specific candidates (keychain, Spotlight/`mdworker`) were checked and found **not to match this symptom**: documented keychain issues on macOS produce visible auth prompts or login failures, not silent multi-minute hangs (`#81707`, `#9403`); the one Spotlight-indexing report found concerns the separate Claude *Desktop* app's cache directory, not the CLI's `~/.claude/projects/`, and does not transfer to this investigation without further evidence.
- **Caution** (flagged by web-researcher): a search-engine summary claimed an official changelog entry "up to 67% faster on 40MB+ sessions" — this text could **not** be found in the actual `CHANGELOG.md` on GitHub and should be treated as unconfirmed, possibly fabricated by the summarizer. Do not cite it as fact.

## Constraints & Risks

- [W]/[V] combined: the reporter's specific hypothesis — that delay scales with **idle time alone** — is only partially supported. The one primary-source mechanism that ties elapsed time to cost (cache expiry) requires elapsed time **and** a transcript over roughly 100k tokens together; one GitHub issue explicitly rules out staleness as a cause of the hang class and blames file size alone. **The evidence available to this brief cannot cleanly separate "old but small" sessions from "new but large" sessions** — no source isolates these variables. Any staleness threshold reported to Plan mode (e.g. "roughly one hour") should be understood as the *cache-expiry* threshold from Anthropic's docs, not a proven trigger for the specific 20-30 minute silent-hang symptom reported here.
- [V] litefactory has **no session-pruning or transcript-retention mechanism** for either its own run logs (`internal/config/paths.go:16-25,79-83` — one log-file set per run, accumulating forever with no cleanup code found) or, necessarily, for Claude's own `~/.claude/projects/*.jsonl` store (which is entirely outside this repository's code and was not directly inspected). If litefactory's own sessions (and by extension the Claude sessions it resumes) are long-lived and repeatedly resumed over weeks/months without any pruning, transcripts could grow into the size range implicated by the GitHub issues above — turning "idle time" and "transcript size" into correlated variables in practice, even though they are causally distinct in Anthropic's own documentation.
- [V] `internal/harness/settings.go:114` denying `claude` read access to `~/.claude/**` is a real, verified fact about this codebase, but its *consequence* for resume behavior is unverified — flagged as the top hypothesis to test, not a confirmed cause.
- [V] Two genuinely unbounded/unverified wait points exist on litefactory's own side before `claude` is even started: `cloneGate.Acquire` (unbounded by design) and `ingestAttachments` (duration not verified). Any incident investigation should rule these out first, since they would produce the same "no log update" symptom for reasons entirely unrelated to Claude's resume mechanics.
- [V] Logging is structurally blind to both classes of delay: litefactory's own pre-`Start()` window and `prepare()`'s single end-of-function log line, and the Claude binary's own internal bootstrap time between `cmd.Start()` (`runner.go:590`, logged) and its first `stream-json` event (`harness/stream.go`, logged separately). **The current logs cannot distinguish "litefactory was waiting" from "the claude subprocess was waiting" for a real incident**, which is a diagnostic gap independent of root cause.

## Open Questions

1. **[Highest priority]** Does the `~/.claude/**` read-deny sandbox in `internal/harness/settings.go:114` cause `claude --resume` to fail-slow (retry/fallback/silent-swallow) rather than fail-fast, when it cannot read its own session transcript? This is untested by either sub-agent and would be a litefactory-caused regression rather than an upstream bug — recommend Plan mode scope a direct reproduction (spawn `claude --resume <id>` by hand with and without the deny-list settings, on a session confirmed to be several hours-to-days idle, and compare).
2. Can litefactory's logging be extended to emit a log line immediately before `cmd.Start()` (already true, per `runner.go:590`, but currently *after* Start returns, not before/around it) and to timestamp the interval between `Start()` and the first `stream-json` event distinctly from the interval spent in `prepare()`? Without this, a real incident's logs cannot attribute the delay to litefactory vs. the `claude` binary vs. Anthropic's network/service side.
3. Does the reported 20-30 minute delay correlate with **transcript size** (token count / `.jsonl` file size of the resumed session) rather than, or in addition to, elapsed idle time? This is answerable only by instrumenting a real incident (question 2) and correlating against the actual session's transcript size — not answerable from source reading alone.
4. Is `cloneGate.Acquire` (`internal/daemon/gate.go:86-100`, unbounded wait, no timeout by design) ever held for tens of minutes by a sibling turn in practice? This would produce an identical "no log update, delay before first log line" symptom for a reason unrelated to Claude resume at all, and should be ruled out from real incident data (are other turns on the same clone running concurrently during the reported delays?).
5. What is the actual runtime cost of `ingestAttachments` (`internal/turn/prepare.go:225`)? Not verified in this tour — worth checking directly if any of the reported slow-resume incidents involved comments with large attachments.
6. Is `internal/daemon`'s scheduler/tick loop (beyond `gate.go`, not opened in this tour) capable of introducing its own multi-minute wait before a turn's `Execute` is even called? Needs a follow-up codebase read scoped to `internal/daemon` if question 1 and 2's instrumentation do not explain an observed incident.
7. Would switching litefactory to `claude --continue` (community-reported as a faster path for cases equivalent to "most recent conversation in this directory") be semantically compatible with litefactory's per-session, per-segment resume model (`internal/naming/session.go`, one deterministic UUIDv5 session ref per segment, not "most recent in cwd")? This needs to be checked against litefactory's actual segment/session semantics before being considered a candidate fix — likely not a drop-in replacement, but worth Plan mode's explicit ruling-out.
8. Is there a `cleanupPeriodDays`-equivalent lever litefactory could set for the `claude` processes it spawns, or does litefactory's generated settings file (`harness/settings.go`) already control retention for the sessions it creates? Not checked in this tour.

**Web-access note.** `web-researcher` did have live web access on this run (WebSearch/WebFetch succeeded and returned GitHub issue and documentation content), so the above external findings are first-hand fetches from this run, not blocked by a missing tool label. They remain tagged `[W]` because they describe *upstream* (Anthropic-side) behavior that this brief cannot verify against litefactory's actual runtime — not because access was unavailable.

## Recommended scope for Plan mode

**In scope:**
- Instrumenting litefactory's own logging (open question 2) to make the litefactory-vs-claude-binary attribution possible for future incidents — this is the single highest-leverage, lowest-risk change and should probably ship regardless of what causes the current incidents.
- A direct, hands-on reproduction of open question 1 (the `~/.claude/**` deny-list interaction with `--resume`), since it is the one hypothesis internal to this codebase and within litefactory's power to fix if confirmed.
- A decision on whether litefactory needs any session/transcript retention policy of its own (open question 8, and the general accumulation risk noted in Constraints & Risks), independent of whether it's the root cause of this specific report.

**Out of scope (do not plan against unverified externals):**
- Any fix predicated on the *staleness-alone* hypothesis as originally reported — the evidence in this brief only supports staleness-combined-with-size (cache expiry) or size-alone (upstream hangs), not staleness in isolation. Plan mode should not scope a fix narrowly around "session age" without first confirming via instrumentation (question 2/3) that age, independent of size, is actually the driver.
- Any change to Anthropic's own `claude` binary internals — those are entirely outside this repository and can only be worked around (flag switch, transcript pruning, sandbox change), never fixed directly.
- Acting on the unconfirmed "67% faster on 40MB+ sessions" changelog claim (flagged by web-researcher as likely fabricated) — do not cite or plan around it.

### Console text format vs. daemon.log JSON format — resolved in first revision, now landed as code

The reporter's clarification ("exactly what litefactory shows now when I do `litefactory daemon run`") makes the exact shape of the console output load-bearing. Findings from the first follow-up revision:

- `logging.New` (`internal/logging/logging.go:37-51`) builds a single `slog.HandlerOptions{Level: opts.Level}` and constructs **two handlers sharing it**: `slog.NewTextHandler(opts.Console, handlerOpts)` for the console (`logging.go:42`) and `slog.NewJSONHandler(opts.File, handlerOpts)` for `daemon.log` (`logging.go:44-45`). Both are **stock, unmodified stdlib handlers** — no `AddSource`, no `ReplaceAttr`, no custom formatter, no colorization. `[V, this revision]`
- Confirmed by test (`internal/logging/logging_test.go:12-30`, `:68-83`): the console output for e.g. `logger.Info("push", slog.String("branch","main"))` is literally default `slog.TextHandler` shape — `time=... level=INFO msg=push branch=main`, with `WithGroup` producing dotted-prefixed keys (`git.branch=main`). `[V, this revision]`
- **Conclusion: "exactly what `daemon run` shows" = plain `slog.TextHandler` text, not `daemon.log`'s JSON.** Since `daemon.log` is the only persisted, taillable record of what the daemon logged, a bare `litefactory logs` view that must show "exactly" the `daemon run` console appearance needs to **re-render each JSON record from `daemon.log` back into `TextHandler`-equivalent text**. This is confirmed, per Current Implementation State above, to now be exactly what `cmd_logs_slog.go`'s `newSlogTextSink` does. `[V, this revision]` for the mechanism/need; `[V, 2nd revision]` that it has now been built.
- `daemon run` (foreground, interactive terminal) and `daemon start` (backgrounded via launchd) are **the same code path** — `daemon start` resolves this same binary and has launchd exec `[abs, "daemon", "run"]` as a child process (`internal/cli/cmd_daemon_agent.go:349-363`); there is no separate in-process "background daemon." The only divergence is whether stdout is a tty: under launchd, stdout is redirected to `launchd.out.log`/`launchd.err.log` (`internal/launchd/plist.go:45-46,124-128`), so `logging.IsTerminal(os.Stdout)` is `false` and the console `TextHandler` is **never installed** for a launchd-run daemon — only the JSON file handler receives records. Under a manual foreground `daemon run` at a terminal, both handlers fire. `[V, this revision]` This means: for a daemon actually running as a background service (the normal `daemon start` operating mode), `daemon.log` is the *only* record that ever existed of what would have appeared on a foreground console — there is no separate stashed copy of "the text that would have printed." Re-rendering from the JSON in `daemon.log` is therefore not just a nicety but the only way to reconstruct that view when the daemon isn't running attended in a terminal, which is the common case this feature is meant to serve.

## Domain / Problem Space

litefactory currently has two kinds of "log" that are conceptually and physically separate:

1. **Issue/run-scoped logs** — one JSONL file per run, keyed to a GitHub issue, fully exposed today via `litefactory logs <issue>` with rich options (`--run`, `--raw`, `--grep`, `--only`, `-f`).
2. **Daemon/system-scoped logs** — `daemon.log`, a single JSON-line file capturing every daemon tick and every structured event across all repos/issues, already written continuously by the running daemon. As of this revision, it is now partially exposed through the CLI (bare `litefactory logs`, rendered as text, tailed, followable — see Current Implementation State) but without level filtering, grep/kind filtering, or a write-time level override yet.

The reporter's need is squarely for visibility into category 2, streamed, rendered to look like the console output they already see from a foreground `daemon run` (confirmed to be plain `slog.TextHandler` text — not JSON, and not a curated subset), with the ergonomic `-f` follow behavior that already exists for category 1. The complaint about "the help needs to move" is a consequence of how the `logs` command's argument parsing behaved **before this branch's implementation work**: since `issue` was a required positional, running `logs` with no arguments was treated as a usage error and short-circuited into printing that command's help/usage block instead of doing anything log-related. Whether the "help needs to move" half of the ask (US-4) has actually landed alongside the routing change (US-1) is unconfirmed and is the single most important open item carried forward by this revision — see Open Question 13. `[V]`

There is no evidence of a "tick" concept meaning anything other than the daemon's poll-and-dispatch loop (`internal/daemon/tick.go`) — `[V]` this matches the reporter's usage ("the ticks litefactory works on").

The reporter's second ask — a verbosity keyword — sits on top of an existing but CLI-invisible config feature (`log_level` in `config.yaml`, default `info`). `plan_brief.md` settled the design question of what the keyword should control (both a display-time filter and a write-time override, per US-5/US-6), but neither is implemented yet.

- **No IPC with the daemon.** `cmd_logs.go` documents "no daemon IPC of any kind (AC-5.8) — no socket, no signal, no lock." Confirmed as an ongoing constraint by `TestLogsUsesNoDaemonIPC`'s behavioral check (daemon stopped, `logs` still works, no lock file created) — see Codebase Context, above. `[V, 2nd revision]`
- **Format mismatch — resolved and now implemented.** `daemon.log` is JSON-per-line; the console output the reporter wants matched is plain `slog.TextHandler` text. `cmd_logs_slog.go`'s `newSlogTextSink` is confirmed to implement exactly this re-rendering. `[V, 2nd revision]`
- **Verbosity is write-time and process-wide today, not a display-time filter — still true, feature not yet built.** The daemon's logger level (`log_level` in `config.yaml`, default `info`) is resolved once at process start (`main.go:65-69`) and shared by both the console handler and the `daemon.log` JSON handler. There is no live/mutable level (no `slog.LevelVar`) and no per-invocation override. `plan_brief.md` records the decision (US-5 display filter + US-6 write-time flag on `daemon run`/`daemon start` specifically, not a global flag) but neither is implemented as of this revision.
- **No log rotation.** `daemon.log` has no observed rotation logic (`FileSink` opens `O_APPEND|O_CREATE` only, `filesink.go:63`) — it will grow unbounded. `plan_brief.md` accepts this as pre-existing M0 debt and scopes the new reader to tolerate truncation defensively rather than fix rotation; `cmd_logs_app.go`'s `followAppLog` is confirmed this revision to include stat-based truncation handling, consistent with that plan. `[V, 2nd revision]`
- **Backward compatibility of `logs <issue>`.** Two existing tests originally pinned the exact bare-`logs`-is-an-error behavior and error strings: `internal/cli/router_test.go:95` and `internal/cli/parse_test.go:222`. `plan_brief.md` calls for these to change deliberately as part of US-4, landed atomically with US-1. **Whether they have actually been updated is unconfirmed this revision** — the codebase-tour that found the new files did not re-run or re-read these specific test bodies for their current content. This is the crux of Open Question 13.
- **Where "help needs to move" lands.** The reporter's phrasing implies command help should be relocated so it's not what `logs` shows by default. `litefactory logs --help` is now confirmed (this revision) to independently and correctly print the command's own usage regardless of the no-issue-argument behavior — these are two different code paths (`errHelpRequested` vs. missing-argument `UsageError`), so relocating one does not affect the other. What remains genuinely open is only whether bare `logs` (no args, no `--help`) still falls through to a usage block today, or has been changed to route to the app log per US-1 — see Open Question 13.

**In scope (as originally recommended, now largely enacted by Plan mode's own artifact):**
- Decide and specify the concrete shape of an app-level/daemon-level log view exposed via the CLI (see former Open Question 3), including whether it lives under the existing `logs` command (with `issue` made optional) or a new command/subcommand.

- A separate `litefactory logs daemon`/`litefactory daemon logs` command.

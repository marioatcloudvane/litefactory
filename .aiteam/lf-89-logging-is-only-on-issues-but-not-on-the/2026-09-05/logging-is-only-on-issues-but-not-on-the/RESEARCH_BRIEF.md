### The `logs` command today

- `internal/cli/cmd_logs.go` (988 lines) implements the whole `logs` command. `newLogsCommand()` declares `Args: ArgSpec{Names: []string{"issue"}, Min: 1}` — the issue is a **required** positional argument. `[V]`
- Flags (`logsOptions.bind`): `--run N`, `--runs`, `--raw`, `--only`, `--grep`, and **`-f`/`--follow`** ("follow the run as events are written"). `[V]`
- `runLogs` → `loadLogTarget` opens the SQLite store, reads the session + its runs for the given issue, then **closes the DB** before branching into `writeRunList` / `tailLog` / `copyLog` / `writeRun`. `[V]`
- `tailLog(ctx, sink, path, followInterval=250ms, finished)`: pure polling via `time.NewTicker`, no fsnotify — documented as deliberate ("daemon is a separate process appending, a watcher buys nothing over a ticker"). Stops on a terminal event (`"result"`, `"turn.completed"`, `"turn.failed"`) or `ctx.Done()`. Reads via `bufio.Reader.ReadBytes('\n')` (not `Scanner`, to avoid the 64KB token limit). `[V]`

- Per-issue run logs live at `naming.RunLogPath(home, ref, ordinal)` / `naming.RunMetaPath(...)`, under `$LF_HOME/logs/runs/...`, one JSONL file per run. `internal/turn` is commented as the writer of the run + meta files (not independently confirmed by reading `internal/turn`). `[V]` / `[W]` for the writer attribution specifically.
- The daemon log has **no DB row, no run ordinal, and no per-issue association** — `loadLogTarget`/`streamLog` are issue/run-scoped and DB-backed, and are not directly reusable for a daemon-wide view; a bare-`logs` daemon view needs its own line-reading path independent of these. `[V, this revision]`

### Existing logging infrastructure

- `internal/logging/logging.go` (122 lines): one process-wide `*slog.Logger`, fanned out to two handlers — a text handler to the console (only when the console is a terminal) and a JSON handler that **always** writes every record to a file. No package-level global logger; passed by struct field. `[V]`
- `internal/config/paths.go:20-22,73-83`: `LogsDir() = $LF_HOME/logs`, `RunsDir() = $LF_HOME/logs/runs`, `DaemonLogPath() = $LF_HOME/logs/daemon.log`. `daemon.log` is a **pre-existing, distinct, app-level log file that already exists on disk today** — it is simply never read by any `logs`-family CLI code. Only `RunsDir()`/`naming.RunLogPath` and the DB are read by `cmd_logs.go`. `[V]`
- `internal/logging/filesink.go` (86 lines): `FileSink` opens `daemon.log` lazily on first write (append mode, `O_APPEND|O_CREATE`), relies on process umask `0o077` for 0700/0600 perms (no explicit `Chmod`). Thread-safe via mutex. **No rotation logic observed** — `daemon.log` grows unbounded as currently implemented. `[V]`
- `daemon.log` (JSON, via `slog.NewJSONHandler`) and per-issue run logs (JSONL, rendered by `cmd_logs.go` with a `--raw`/formatted split) are **structurally separate today with no shared reader abstraction**. Any feature that surfaces both through one command needs to bridge two different formats and two different locations. `[V]`

### Console text format vs. daemon.log JSON format — resolved this revision

The reporter's clarification ("exactly what litefactory shows now when I do `litefactory daemon run`") makes the exact shape of the console output load-bearing. New findings:

- `logging.New` (`internal/logging/logging.go:37-51`) builds a single `slog.HandlerOptions{Level: opts.Level}` and constructs **two handlers sharing it**: `slog.NewTextHandler(opts.Console, handlerOpts)` for the console (`logging.go:42`) and `slog.NewJSONHandler(opts.File, handlerOpts)` for `daemon.log` (`logging.go:44-45`). Both are **stock, unmodified stdlib handlers** — no `AddSource`, no `ReplaceAttr`, no custom formatter, no colorization. `[V, this revision]`
- Confirmed by test (`internal/logging/logging_test.go:12-30`, `:68-83`): the console output for e.g. `logger.Info("push", slog.String("branch","main"))` is literally default `slog.TextHandler` shape — `time=... level=INFO msg=push branch=main`, with `WithGroup` producing dotted-prefixed keys (`git.branch=main`). `[V, this revision]`
- **Conclusion: "exactly what `daemon run` shows" = plain `slog.TextHandler` text, not `daemon.log`'s JSON.** Since `daemon.log` is the only persisted, taillable record of what the daemon logged, a bare `litefactory logs` view that must show "exactly" the `daemon run` console appearance will need to **re-render each JSON record from `daemon.log` back into `TextHandler`-equivalent text** (e.g. by decoding each JSON line into `slog.Record`-shaped fields and re-emitting through a `TextHandler`, or hand-formatting to match). It cannot be a raw `cat`/tail of `daemon.log` as-is — that would show JSON, not the console appearance the reporter is asking to match. This is new implementation work, not a rendering flag toggle. `[V, this revision]` for the mechanism; the "needs new re-rendering code" conclusion is `[Assumption]` grounded directly in the two facts above.
- `daemon run` (foreground, interactive terminal) and `daemon start` (backgrounded via launchd) are **the same code path** — `daemon start` resolves this same binary and has launchd exec `[abs, "daemon", "run"]` as a child process (`internal/cli/cmd_daemon_agent.go:349-363`); there is no separate in-process "background daemon." The only divergence is whether stdout is a tty: under launchd, stdout is redirected to `launchd.out.log`/`launchd.err.log` (`internal/launchd/plist.go:45-46,124-128`), so `logging.IsTerminal(os.Stdout)` is `false` and the console `TextHandler` is **never installed** for a launchd-run daemon — only the JSON file handler receives records. Under a manual foreground `daemon run` at a terminal, both handlers fire. `[V, this revision]` This means: for a daemon actually running as a background service (the normal `daemon start` operating mode), `daemon.log` is the *only* record that ever existed of what would have appeared on a foreground console — there is no separate stashed copy of "the text that would have printed." Re-rendering from the JSON in `daemon.log` is therefore not just a nicety but the only way to reconstruct that view when the daemon isn't running attended in a terminal, which is the common case this feature is meant to serve.

### Verbosity / log level — new findings this revision

The reporter's ask for "a keyword for verbosity level (eg info, ...)" turns out to name a feature that **already half-exists** in the codebase, but only as static, restart-required configuration — not as a runtime keyword on any command.

- **A `log_level` config setting already exists**: `internal/config/config.go:91` — `Settings.LogLevel string \`yaml:"log_level"\``. Default is `"info"` (`DefaultLogLevel = "info"`, `config.go:446`, seeded into a fresh config at `config.go:368`). `[V, this revision]`
- **Validation already exists**: `internal/config/validate.go:183-192` (`validateLogLevel`) rejects an empty value ("must not be empty; use debug, info, warn or error") and anything `slog.Level.UnmarshalText` can't parse; wired in at `validate.go:115`. `[V, this revision]`
- **Parsing already exists and already accepts exactly the vocabulary the reporter asked for**: `logging.ParseLevel(s string) (slog.Level, error)` (`internal/logging/logging.go:99-108`) accepts `"debug"|"info"|"warn"|"error"`, case-insensitive (confirmed by `internal/logging/logging_test.go:95`), empty string defaults to Info. `[V, this revision]`
- **Wiring is single-shot, at process start, shared by both sinks**: `cmd/litefactory/main.go:103-117` (`configuredLevel()`) loads config and calls `logging.ParseLevel(cfg.Settings.LogLevel)`, falling back silently to `slog.LevelInfo` on any failure (deliberate — it must work before `init` has run). This value is passed into the single `logging.New(logging.Options{Level: ..., Console: ..., File: ...})` call at `main.go:65-69` — the **only** call site of `logging.New` in the repo. Both the console `TextHandler` and the file `JSONHandler` share this one `Level` (`logging.go:38,42,44-45`). `[V, this revision]`
- **What does NOT exist, confirmed by exhaustive repo-wide search**: no `--verbose`/`-v` CLI flag, no `--log-level` flag, no `LF_LOG_LEVEL` or any other log-level environment variable, and no `slog.LevelVar` (mutable/live level) anywhere in the codebase. The only `--verbose` hits in the repo belong to the Claude harness's own invocation of the `claude` CLI (`internal/harness/runner.go:39,421`) — unrelated to litefactory's own logger. **Today, the only way to change verbosity for anything (the `daemon run` console, or `daemon.log`) is editing `log_level:` in `config.yaml` and restarting the process.** There is no per-invocation override and no way to change it while a daemon is already running. `[V, this revision]`

This is a materially useful finding for Plan mode: the level vocabulary, the parser, and the validation all already exist and match the reporter's request ("eg info, ...") almost exactly — what's missing is purely a **CLI-facing entry point** for it, and a decision about *which* of two different things "verbosity keyword" should control (see Open Questions, below).

### Convention for adding this command

- One `*Command` per `cmd_<group>.go` file, registered with one line in `internal/cli/commands.go:8-20` (9 commands today: `init`, `repo add/list`, `daemon run/start/stop/status`, `logs`, `task clean`). This is the documented, established pattern for adding or restructuring a command. `[V]`
- `ArgSpec{Min: 0}` is already a supported mechanism in `internal/cli/command.go` — nothing structurally prevents making the `issue` positional optional on `logs` (this is a seam that exists, not a recommendation either way). `[V]`
- `tailLog`'s poll-based follow implementation is directly reusable in shape (same 250ms-ticker + offset-tracking pattern) for a "follow the daemon log" feature — it is the one existing "follow a growing file" pattern in the codebase. `[V]`
- The sole call site of `logging.New` is `cmd/litefactory/main.go:65-69`, inside `run(args []string) int`, which runs **before** the router dispatches to any subcommand (`main.go:79`). `configuredLevel()` (`main.go:66`) is likewise called before the router sees `args` at all. This means today there is no seam for a per-command flag (e.g. `logs --level debug`) to influence what level was captured at write time — that decision is made and the logger constructed before command-specific flag parsing happens. A verbosity keyword that's meant to change *live write-time* behavior would need either a hand-rolled pre-scan of `args` in `main.go` ahead of `logging.New`, or a broader restructuring; a verbosity keyword that's meant to *filter what's already been written* when displayed needs no such change and can be a normal flag on the `logs` command's own `FlagSet` (`cmd_logs.go:75-87` is the existing pattern for command-local flags). `[V, this revision]`

## Domain / Problem Space

litefactory currently has two kinds of "log" that are conceptually and physically separate:

1. **Issue/run-scoped logs** — one JSONL file per run, keyed to a GitHub issue, fully exposed today via `litefactory logs <issue>` with rich options (`--run`, `--raw`, `--grep`, `--only`, `-f`).
2. **Daemon/system-scoped logs** — `daemon.log`, a single JSON-line file capturing every daemon tick and every structured event across all repos/issues, already written continuously by the running daemon, but with **zero CLI exposure**. The only surfaced fragment of this today is a single timestamp (`daemon status`'s "last tick").

The reporter's need is squarely for visibility into category 2, streamed, rendered to look like the console output they already see from a foreground `daemon run` (confirmed this revision to be plain `slog.TextHandler` text — not JSON, and not a curated subset), with the ergonomic `-f` follow behavior that already exists for category 1. The complaint about "the help needs to move" is a consequence of how the `logs` command's argument parsing currently behaves: since `issue` is a required positional, running `logs` with no arguments is treated as a usage error and short-circuits into printing that command's help/usage block instead of doing anything log-related. `[V]`

There is no evidence of a "tick" concept meaning anything other than the daemon's poll-and-dispatch loop (`internal/daemon/tick.go`) — `[V]` this matches the reporter's usage ("the ticks litefactory works on").

**New in this revision**: the reporter's second ask — a verbosity keyword — sits on top of an existing but CLI-invisible config feature (`log_level` in `config.yaml`, default `info`). The domain question isn't "does litefactory have a levels concept" (it does, fully formed) but "what should a verbosity *keyword on the `logs` command* actually do," given that levels below the configured `log_level` are never written to `daemon.log` in the first place. See Open Questions.

## Constraints & Risks

- **Redaction invariant.** `cmd_logs.go` is under a build-breaking guard preventing it from importing `internal/redact`, because per-issue log output is unredacted by design (S-7). If daemon-log content is ever surfaced through the same command/file, whoever implements this must confirm whether `daemon.log` content carries the same "always unredacted, operator already owns `$LF_HOME`" trust assumption, or whether it needs different handling. This wasn't contradicted by anything found, but wasn't explicitly confirmed for daemon-level output either. `[V]` for the guard's existence; `[Assumption]` that the same trust model extends to daemon.log content.
- **No IPC with the daemon.** `cmd_logs.go` documents "no daemon IPC of any kind (AC-5.8) — no socket, no signal, no lock." Any new follow-the-daemon-log feature should stick to the same file-polling pattern used by `tailLog`, not attempt to talk to a running daemon process directly. `[V]`
- **Format mismatch — resolved to a specific direction this revision.** `daemon.log` is JSON-per-line (raw slog JSON handler output); the console output the reporter wants matched is plain `slog.TextHandler` text. A unified `logs` experience now has a concrete target: re-render `daemon.log`'s JSON records into `TextHandler`-equivalent text, rather than passing JSON through raw or inventing a third format. This is more implementation work than a pass-through would have been (decode each JSON line, reconstruct attrs/ordering, re-emit as text) but the target shape is no longer ambiguous. `[V, this revision]`
- **Verbosity is write-time and process-wide today, not a display-time filter.** The daemon's logger level (`log_level` in `config.yaml`, default `info`) is resolved once at process start (`main.go:65-69`) and shared by both the console handler and the `daemon.log` JSON handler. There is no live/mutable level (no `slog.LevelVar`) and no per-invocation override. This has a direct consequence for any "verbosity keyword" on `logs`: if the daemon is running at its default `info` level, **Debug-level lines were never written to `daemon.log` at all** — a `logs --level debug` style flag can only ever surface what's ≥ the level the daemon was actually configured with at write time; it cannot retroactively reveal Debug detail that was silently dropped. Plan mode must decide whether "verbosity keyword" means (a) a display-time filter on `logs` output (cheap, but capped by what was captured), (b) a way to raise the live daemon's write-time level (requires either a config change + restart, as today, or new work to make the level mutable/settable without a restart), or (c) both. `[V, this revision]`
- **No log rotation.** `daemon.log` has no observed rotation logic (`FileSink` opens `O_APPEND|O_CREATE` only, `filesink.go:63`) — it will grow unbounded. Not a new risk introduced by this feature, but worth flagging since a "follow the daemon log" feature makes this file more visible/relied-upon than it is today.
- **Backward compatibility of `logs <issue>`.** Two existing tests pin today's exact behavior and error strings: `internal/cli/router_test.go:95` and `internal/cli/parse_test.go:222` (bare-`logs` usage error). Any change to `logs`'s argument requirements (e.g. making `issue` optional so bare `logs` means something else) will need these updated, and the ~870 unread lines of `internal/cli/cmd_logs_test.go` likely contain more follow-mode (`-f`) test cases that would need auditing for regressions. `[V]`
- **Where "help needs to move" lands.** The reporter's phrasing implies command help should be relocated so it's not what `logs` shows by default. The codebase already has a `help` command/flag path (`litefactory help`, `--help`, `-h`) and a `writeGlobalUsage` for the fully-bare `litefactory` invocation — these are unaffected by anything in `cmd_logs.go` and already exist as the "true" help entrypoints. What would change, if this request is implemented as described, is only the *specific* case of `logs` with no issue argument no longer falling through to that command's own usage block.

10. **NEW — what should the "verbosity keyword" actually control?** The reporter's ask ("a keyword for verbosity level (eg info, ...)") is compatible with at least two different designs, and the codebase already supports the vocabulary (`debug`/`info`/`warn`/`error`, via `logging.ParseLevel`) for either:
    - **(a) A display-time filter on `logs` output** — e.g. `litefactory logs --level debug` (or a bare positional keyword) shows only records at/above the given level from what's already in `daemon.log`. Cheap to build (a filter predicate over decoded JSON records, similar in spirit to the existing `--grep`/`--only` flags on issue logs) but **capped by what the daemon actually wrote** — if the daemon is running at its default `info` level, no Debug lines exist to surface, filter or not.
    - **(b) A way to change the live daemon's write-time level** — e.g. so an operator can say "start logging at debug" without hand-editing `config.yaml` and restarting. This is a bigger change: today the level is resolved once at process start (`main.go:65-69`) and there is no mutable `slog.LevelVar` anywhere, so making the daemon's level changeable at runtime (or even just settable via a new CLI flag for a fresh `daemon run`/`daemon start` invocation) is new work, not a rendering change.
    - **(c) Both** — a flag on `daemon run`/`daemon start` to set the level a fresh daemon process starts at (reusing the existing `config.yaml`/`ParseLevel`/`validateLogLevel` machinery, just adding a CLI override path per invocation), plus a separate display-time filter on `logs`.
    Recommendation: **(c) is the most complete reading of "a keyword for verbosity level," but (a) alone is the minimum viable interpretation of the reporter's one-line ask** and requires no changes to `daemon run`/`daemon start`/`config.yaml` at all.

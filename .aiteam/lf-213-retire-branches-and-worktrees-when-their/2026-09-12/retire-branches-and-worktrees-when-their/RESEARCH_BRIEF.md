# Research: retire branches and worktrees (#213)

Status: complete — bounded Research only. No implementation or retirement performed.

## Request and scope

Sketch the lifecycle paths, including successful validation, abandonment/duplicate closure, and external completion, and recommend a simple policy that handles each safely. This request is clear enough to research without questions. The recommendations below are proposals for Plan, not previously approved implementation decisions. Repository counts in the issue are owner-reported historical measurements, not a current inventory verified by this run.

## Recommendation

Use one periodic retirement evaluator, also exposed as an operator preview. Three facts do different jobs: **GitHub closure establishes inactivity; fresh commit reachability establishes preservation; elapsed time controls worktree retention.** Neither successful validation nor a closed issue alone proves a branch disposable.

Remove clean, safely backed-up worktrees after the configured retention period. Automatically delete branches only when their exact tips are reachable from the configured remote base. Keep abandoned and squash/rebase-integrated branches when that proof fails; they consume little checkout space and preserve original commits. Offer archive-and-delete as a later, explicit operator workflow rather than adding tags automatically in this feature.

Apply the same rules regardless of who closed the issue or its closure reason. Keep cleanup separate from workflow acceptance: external closure can permit resource retirement without fabricating a passed Validate run or changing retained acceptance decisions.

## Lifecycle paths

“Expired” means the worktree retention rule below is satisfied. All deletion cells are conditional on the shared safety gates. Local and remote branch tips are assessed separately; one can contain commits the other lacks.

| Path | Worktree | Local branch | Remote branch |
|---|---|---|---|
| Research/Plan/Implement completed, Validate passed, or story accepted; owning feature still open | Keep | Keep | Keep. None of these events proves delivery. |
| PR created, approved, conflicted, checks pending, or closed without merge; issue open | Keep | Keep | Keep. |
| Factory confirms merge and parent closure | Remove when expired | Delete after its worktree is gone and its tip is in base | Delete when its tip is in base; need not wait for checkout retention. |
| Someone else merges and closes the issue; local workflow still appears unfinished | Same as factory completion | Same reachability test | Same reachability test; do not require a local Validate record. |
| Issue closed as won't-do, duplicate, invalid, or manually “completed,” with unmerged commits | Remove when expired only if local commits remain reachable from the fresh remote task branch or base | Keep under the conservative unmerged-branch policy | Keep; closure reason does not preserve commits. |
| Closed issue with no task-specific commits | Remove when expired | Delete once no worktree uses it and tip is in base | Delete if present and tip is in base. No PR is necessary for proof. |
| PR squash-merged, rebase-merged, cherry-picked, or changes reimplemented elsewhere; issue closed | Remove when expired if original local commits are still backed up remotely | Keep unless exact commit ancestry independently passes | Keep unless exact commit ancestry independently passes. Equivalent file content is insufficient. |
| PR merged, but issue remains open or is reopened before cleanup | Keep | Keep | Keep. Do not close the issue just to enable cleanup. |
| Closed issue, dirty/untracked work or local commits absent from fresh remote task branch and base | Keep and explain | Keep | Conservatively defer this task's retirement; resolve retained local work first. |
| Remote task branch already deleted; local tip is reachable from fresh remote base | Remove when expired | Delete after worktree removal | Already absent; report as such. Missing task upstream alone is not a blocker. |
| Remote task branch already deleted; original local commits not in base, including externally squashed work | Keep | Keep: this may now be the remaining original history | Already absent; never treat absence as proof of preservation. |
| Closed issue with remote branch only, no recorded checkout | Nothing to remove | If present, independently assess it | Eligible on closure plus ancestry; worktree existence is not required. |
| Closed managed child while parent remains open, or child never had independent working state | Do not remove parent resources | Do not infer branch ownership from child closure | Evaluate only the actual owning task/session. |
| Failed, interrupted, cancelled, or abandoned run on a now-closed issue | Same expiry and preservation checks; failure never relaxes safety | Keep if not in base | Keep if not in base. Pending recovery/effects must be reconciled first. |
| Reopened after retirement | Recreate on the next authorized run | Reuse surviving branch; otherwise create from fresh base | Recreate through ordinary saving as needed; do not resurrect stale tracking refs. |
| Missing checkout, stale Git worktree registration, or earlier partial cleanup | Reconcile confirmed absence and owned administrative entry; never recursively remove an arbitrary directory | Independently re-evaluate | Independently re-evaluate; operations must be repeatable. |
| Unregistered/manual worktree or branch, detached HEAD, wrong branch/path, locked worktree, transferred/deleted/inaccessible issue, missing base, or uncertain ownership | Leave untouched and report unknown/blocked | Leave untouched | Leave untouched. A naming prefix or 404 is not sufficient authorization. |

This covers combinations by applying the lifecycle row first, then the shared gates; there is no separate destructive policy for every GitHub label or closure reason.

## Shared safety gates and execution model

**Ownership and fresh evidence.** Enumerate registered task sessions, including old ones with no pending poll; do not sweep directories by glob or equate `lf/*` naming with ownership. Match the stored repository, task branch, canonical path and Git worktree registration. Refuse base/default branches and branches checked out by another worktree. Confirm remote identity and configured base rather than hardcoding `main`; the current delivery workflow's target is specifically main, while repositories also store a BaseBranch (`internal/store/repos.go:26`). Fetch/prune successfully before evaluating remote reachability, and read issue state directly rather than trusting an old cache. API errors, unavailable Git history, ambiguous refs, permission failures and failed status probes mean skipped/unknown, never eligible. A shallow history unable to prove ancestry is unknown.

**Preserve content.** Worktree removal requires no staged, tracked or ordinary untracked changes and proof that its exact local tip is reachable from either the fresh remote task tip or remote base. This allows a fully pushed abandoned checkout to disappear while its branches preserve the work. It also handles a deleted upstream after a real merge. Do not interpret a previous successful push, ahead count against stale refs, or a PR's historical merged flag as current proof. Ignored files need an explicit check: the simplest policy consistent with “no local-only content” is to skip when ignored content exists, reporting a count/reason without exposing contents. This can retain generated build caches; document that tradeoff rather than silently treating every ignored file as disposable. Use unforced Git removal as the final check too.

**Branches.** For each branch, require its observed tip to be an ancestor of the freshly observed remote base tip. That is stronger than “the PR merged” and includes commits added after a PR merge. Local branches with additional work are not certified by the remote branch passing. Delete local branches only after the associated worktree is removed and no other worktree uses them. Keep unmerged local branches even if the remote backs them up: this deliberately makes the first version's branch rule uniform. No automatic archival, force deletion of unknown history, content-equivalence heuristic, history rewrite, or changes to the base branch.

**Retention.** Recommend the issue's simple rule: closed now and last completed run finished at least `worktree_retain_days` ago. Use the last run regardless of success; never age a running/prelaunch run into eligibility. If there has never been a run but an owned worktree exists, use session creation time only when ownership is certain; malformed legacy timestamps mean skipped/unknown. A session with no resources is a no-op. This rule can remove an old checkout on the first sweep immediately after closure; it does not promise 14 days after closure. If Plan instead wants a post-closure grace period, explicitly change the anchor to the later of last-run completion and confirmed closure time and expose/persist that timestamp. Do not use UpdatedAt, which maintenance itself changes.

**Concurrency.** Acquire the same durable task ownership as execution/delivery and coordinate Git mutation through the clone gate. Re-read latest run/effect state, issue closure, local status, worktree identity and observed refs after acquiring ownership. Skip active work and pending operations that still need the checkout. An explicit cleanup CLI must share daemon coordination; a separate process's mutex alone cannot coordinate clone-wide changes. Preserve the existing lock order. Guard remote deletion against a changed expected head, and local ref deletion against the expected local head. If the chosen remote mutation primitive cannot guard the expected head, that is a design gap, not grounds for an unconditional delete.

GitHub issue closure and Git ref deletion are not one transaction. A reopen immediately after the final read is still possible, as are uncooperative manual filesystem writes. Explain this residual race; fresh checks, normal Git refusal, expected-head protection and preserving every deleted tip in base limit consequences. A reopen starts from retained history or fresh base. Do not claim locks prevent arbitrary external actors from editing files.

**Sweep and preview.** Recommend one bounded daily pass, with a persisted next-due marker so restart storms do not repeat a full scan. Startup runs it only when due, after recovery; the ordinary tick schedules bounded batches rather than walking every checkout each minute. Respect existing GitHub request budgets, rate-limit backoff, and shutdown. Share the evaluator with a listing command that defaults to preview; an explicit apply form invokes the same policy. Preview may refresh remote-tracking refs and query GitHub but never deletes resources, advances retirement state or counts as approval of a later stale result. Apply rechecks everything. Daily automation is the requested feature; the preview capability must be available before enabling it, with release/config documentation that the previously informational retention value becomes active. No additional per-sweep approval is proposed.

**Audit and retry.** Retain task/repository identity, path/ref, observed branch/base SHAs, retention anchor, rule/reason, attempted action and confirmed outcome. Write durable intent before deletion and reconcile uncertain results before retrying; a crash must not be reported as success. One task's failure must not hide others. Report removed, kept, already absent and failed counts per sweep, with per-resource explanations available through a local listing/history view. Keep session identity, run reports, acceptance and delivery records. Clear a worktree path only after confirmed removal/absence; preserve enough ownership data to repair a stale Git registration. Remote rejection or storage failure leaves a visible retryable partial result. Avoid an issue comment for every periodic skip; local history plus a summary is enough for this scope.

## Options, boundaries and next step

The recommended first version uses strict commit ancestry, daily scheduling, last-run retention, conservative ignored-file handling and retained unmerged branches. A broader version could archive unmerged tips to verified remote tags and then delete branches, or accept squash/rebase equivalence; both introduce preservation and policy decisions that are unnecessary to reclaim the full checkout directories. Strict ancestry deliberately leaves some merged-looking remote branches in place and reports why.

Plan should turn these proposals into acceptance criteria, including ignored-content handling and the documented retention anchor, then design the narrow Git API/contract amendments, retirement inventory/audit storage, scheduling budget and cross-process CLI coordination. Validate the lifecycle matrix with existing local bare-origin fixtures and controlled forge responses: dirty/ignored content, stale/failed fetch, differing local/remote tips, squash history, deleted refs, external closure, reopen, concurrent execution, deletion head races, partial crashes and retry. No production cleanup or full test suite was necessary to complete this Research report.

No user-only decision blocks this research sketch. These are recommendations ready for a separate Plan run, not authorization to implement or delete existing resources.
